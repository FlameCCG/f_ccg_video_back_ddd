# 架构与媒体原理

这份文档按当前仓库代码写成，用来把整站和 FFmpeg、MP4、DASH、m3u8 讲到能接追问。分层目录以 `docs/architecture.md` 为准，播放和转码的数字以这份为准。

阅读顺序：先看第 1～4 节，能在两分钟内讲清系统；再看第 5～8 节，顺着一次投稿解释媒体处理；最后用第 13～15 节练习白板、边界和追问。配置数值是默认值或示例值，不要把它们讲成协议规定。

先打开[交互架构图](./diagrams/system-architecture.html)：可切换浅色/深色，并按投稿、转码、搜索、缓存与私信四个视图追链路。

图上的主路径是浏览器 → Gin → MySQL → River → Elasticsearch；转码旁路是 Gin → Kafka → 转码消费者（默认同进程，也可独立运行）→ FFmpeg → MinIO/本地存储。MongoDB 与 Redis 也单独成节点；AI 适配器收在图下方说明卡，OAuth 见正文。分片源对象由上传用例写入存储，这条箭头为避免与转码箭头交叉而在图中省略，不能理解成只由 FFmpeg 写存储。

## 1. 用三句话定位这个项目

这是一个 **Go 单体视频站后端**，按上下文组织代码，默认服务进程承担以下职责，转码另有独立消费者入口：

1. Gin 提供公开接口 `/v1/common`、管理接口 `/v1/admin`、WebSocket（私信、弹幕）。
2. 默认同进程后台：Kafka 转码消费者（可关闭本机消费并独立部署）、River（订 MySQL binlog 同步搜索）、Cron、视频定时发布调度器、聊天 Hub、弹幕 Hub。
3. 对外接对象存储（MinIO 或本地磁盘）、五家 OAuth、SMTP、火山方舟 / Claude（经 Eino）。

公开前缀 `/v1/common`，管理前缀 `/v1/admin`。路由金丝雀 `routes_golden.txt` 现在是 192 条，其中包含 `POST /v1/common/image/upload`，以及 `/uploads` 的 GET 和 HEAD。面试时以这份金丝雀为准。

技术选型可以一口报出来：Go 1.24、Gin、GORM、google/wire、Casbin、JWT、IBM sarama、go-redis、Mongo 官方驱动、Elasticsearch（关键词用 olivere v7，向量用官方 v8）、MinIO、robfig/cron、cloudwego/eino。

## 2. 为什么是单体，面试官爱听的那句

默认 `cmd/server` 仍把转码、River 和定时任务与 HTTP 放在同一进程。现在已提供 `cmd/transcode-consumer` 独立入口：在 HTTP 节点设置 `transcode.localConsumerDisabled: true` 并重启，保持投递；在消费节点运行独立命令，它不受该开关影响，也不启动 HTTP、River 或定时任务。消费者可部署到单独机器以隔离 FFmpeg 的 CPU、磁盘和 GPU 资源。同组消费并发受 topic 分区数和 worker 数约束；跨机器需保证 Kafka 宣告地址、MySQL、Redis 和源存储可达。HTTP App 仍采用后台组件启动失败只记日志并继续的策略；独立消费者启动失败则返回非零退出码。配置与启动命令见[独立消费者说明](../../cmd/transcode-consumer/README.md)和[架构说明第 6.3 节](../architecture.md#63-独立转码入口与节点角色)。

默认 HTTP 服务的启动顺序（`App.Start`，关闭本机消费时跳过转码消费）：River → 视频调度器 → 转码消费者 → Cron → Chat Hub → Danmu Hub。单个后台起不来只记日志，不让 HTTP 起不来。

停止顺序：先把 HTTP 优雅停掉，不再接新请求；然后转码消费者 → 视频调度器 → River → Cron → Chat Hub → Danmu Hub → 等脱离请求的后台任务结束；最后关 Mongo → MySQL → Redis → ES → IP 库 → 刷日志。

## 3. 代码怎么分层（DDD，能指着目录讲）

```text
interfaces/http、ws、cli     只认识 gin、请求体、状态码
        │
application/<上下文>         用例：编排事务、调端口、组读模型 DTO
        │
domain/<上下文>              纯 Go：实体、规则、仓储接口。不 import gin/gorm/redis
        ▲
infrastructure               GORM、Redis、Kafka、FFmpeg、Eino 的实现
bootstrap                    wire 组合根。只有这里把接口绑到实现
```

这张图表示源代码依赖：接口层依赖应用层，应用层依赖领域；基础设施实现 domain 或 application 声明的端口。运行时应用服务会调用注入的基础设施对象，但源码不直接 import 其实现。跨上下文协作通过显式端口或 bootstrap 的薄适配器接线；公共枚举、值类型和当前遗留交叉点，要按实际代码说明，不能只凭目录断言完全隔离。

`gin.Context` 停在接口层。往下只传 `context.Context`、用户 ID、客户端 IP。

读和写是拆开的，但是轻量的，不是两套数据库：

- 写：接口 → 应用 → 领域实体 → 领域仓储接口 → 基础设施把 PO 落进 MySQL。
- 读：接口 → 应用查询 → 查询端口 → 基础设施直接把 PO 拼成和旧接口 JSON 字段一致的 DTO。读模型不进领域层。

这样做能保持前端响应契约，同时避免把数据库表与关联直接当作业务模型。写侧 Video 没有 GORM tag；部分共享值结构仍带 JSON tag，所以当前实现不能概括为“领域绝对没有序列化信息”。

十四个限界上下文：

| 上下文 | 干什么 |
|---|---|
| identity | 注册登录、资料、封禁、经验、硬币 |
| rbac | 角色、菜单、接口资源、Casbin |
| video | 上传用例、投稿、分 P、播放、点赞投币收藏、弹幕、举报 |
| media | 媒体存储能力、转码派发、进度、取消与转码管线 |
| comment | 评论树、点赞、置顶 |
| social | 关注 |
| dynamic | 动态、关注流、已读 |
| chat | 私信，文档在 Mongo |
| notification | 通知内容与已读 |
| search | 关键词、建议、热词、向量 |
| contentops | 站点配置、统计、轮播 |
| ai | 聊天、生图、生视频、找视频 |
| platform | Cron 与运维任务 |
| provisioning | 初始化超管、默认横幅 |

配置用 Viper，支持热更新。没有 `global` 包，也没有在 `init()` 里装配业务。测试不走 wire，手写 fake，离线用 sqlite 和 miniredis。

CLI 一次性任务按优先级只跑一个：`-db` 迁移、`-vp` 分区、`-br` 横幅、`-su` 超管、`-es` 重建搜索索引、`-rs` 同步接口资源、`-rbac` 初始化权限。成功退出码 0，失败 1。

## 4. 一次普通请求怎么走

以「用户打开已发布视频详情」为例。公开详情可匿名访问；携带登录身份时，才额外拼装当前用户的点赞、收藏、投币状态。

1. 公开详情可从可选的登录身份取用户 ID；管理接口必须鉴权，再过 Casbin：主体是角色，对象是路径，动作是 HTTP 方法，匹配器用 `globMatch`，所以 `/v1/admin/**` 这种通配能工作。
2. Handler 只做绑定和校验，然后调 `DetailService.GetVideoDetail`。
3. 详情元数据先看 Redis `video:detail:meta:{id}`，TTL 5 分钟。旁边有一个 generation key，写入用 Lua 比对代数，避免「先读到旧状态、后写入」把刚失效的缓存又填回去。
4. 播放量、点赞这些计数以 Redis `video:detail:stats:{id}` 为准，每 5 分钟由 Cron 刷回 MySQL。详情接口读的是这份热计数，不是每次 `UPDATE videos SET views=views+1`。
5. 资源列表按清晰度排序。`自适应` 排最前，然后 4K、1080 高码率、1080、720、360。前端看 `format`：`dash` 走 dash.js 播 `manifest.mpd`，`mp4` 用原生 video 播直链。

鉴权使用 JWT：access 和 refresh 用不同密钥，配置过期单位是天；access 带 uid、username，refresh 带 uid。当前没有服务端 token 黑名单。封禁事务提交后写穿 `user:status:{id}`，并递增 generation 防止在途旧值回填；Redis 正常时后续请求应很快读到新状态，写穿失败时不能承诺立即生效，缓存 TTL 为 60 秒，未命中会回源 MySQL。`JwtAuth` 拦截永久封禁；临时封禁主要由内容写接口的 `UserBanCheck` 检查，不能说所有接口都禁止。封禁记录在 `user_ban_records`，Cron 每 5 分钟清理到期封禁，内容请求也可能触发到期解封。

## 5. 从零听懂「视频文件」

面试官如果问 m3u8，先把四个词分开，再告诉他这个项目产出哪一种。

### 5.1 编码和容器不是一回事

编码（codec）负责把画面和声音压小。**新生成的转码产物**用 H.264：CPU 用 `libx264`，NVIDIA 用 `h264_nvenc`；有音轨时编码 AAC-LC、128 kbps，DASH 和共享音轨只取第一条 `0:a:0`。能直出的上传源片可能原样保留，不能说数据库里所有视频文件都重新编码了。

容器（container）负责把压缩后的样本、时间戳、索引装进一个文件。**新生成的播放产物主要用 MP4 容器**；上传源片可能是其他容器，而服务端的 `_source_<hash>.mp4` 对象名也不能证明里面是浏览器能播的 MP4。ffprobe 会看品牌、profile、像素格式。下面这些源会被判定为「浏览器不能直接播」，从而进入规范化重编码：

- QuickTime 品牌（`major_brand` 以 `qt` 开头，或兼容品牌里有 `qt` 却没有已知 MP4 品牌）
- 视频不是 H.264
- profile 不是 baseline / constrained baseline / main / high
- 像素格式不是 `yuv420p`、`yuvj420p`、`nv12`
- H.264 level 大于 52
- 有音轨但不是 AAC-LC

友好的品牌包括 `isom`、`mp41`、`mp42`、`avc1`、`dash` 等。

### 5.2 MP4 里的 moov，以及 faststart

一个 MP4 里除了画面样本，还有一个叫 **moov** 的盒子，它是目录：每帧在文件的哪个字节、时长多少。如果 moov 在文件末尾，播放器必须先把文件读到头（或先发一次 Range 把尾巴拉下来）才能开播。

**faststart** 是在编码结束后把 moov 挪到文件头。本项目对可随机写的成片加：

```text
-movflags +faststart
```

分段编码的中间块不加，因为最后用 `-c copy` 拼装时会统一加。如果输出是管道或 TCP（历史遗留分支），改成 `-movflags frag_keyframe+empty_moov`，因为那种输出不能回头改文件头。现在的正式路径是先落本地文件再上传，不走边转边传。

### 5.3 HTTP Range 是什么

播放器不会一次把 2GB 下完。它发 `Range: bytes=0-` 或某个区间，服务器回 **206 Partial Content**。MinIO 和静态文件服务自己支持 Range，本仓库没有再写一个 Range 服务器。

faststart 加上 Range，渐进式 MP4 才容易快速起播、拖动。当前 DASH 用初始化文件加 `.m4s` 媒体分片，播放器根据 MPD 中的 SegmentTemplate 和 SegmentTimeline 请求对应文件并选择 Representation。`-seg_duration 4` 是目标分段时长，实际边界和尾段时长以 FFmpeg 原生生成的时间轴为准，不能用固定秒数替代。

### 5.4 码率、CRF、CQP

码率是每秒多少比特。库里的 `bitrate` 单位是 **kbps**。ffprobe 优先用容器的 `bit_rate`，没有就用视频流的，再没有就用 `文件大小 × 8 / 时长`，然后整数除以 1000。

CRF（CPU，`-crf`）和 CQP（GPU，`-rc vbr -cq`）是质量旋钮，不是「每秒必须正好 N 千比特」。数字越小，画质越高，文件越大。本项目在质量旋钮外面再加 `-maxrate` 和 `-bufsize`（bufsize 是 maxrate 的 2 倍），这叫 capped CRF/CQP：平时按质量走，峰值不许超过这条线。

零配置时的质量数字（yaml 里如果写了，以 yaml 为准）：高档 CRF 18；中档 CPU 23、GPU 22；720 档代码兜底 22（示例 yaml 常写 24）；360 档代码兜底 26（示例 yaml 常写 28）。GPU preset 默认 `p4`，CPU preset 默认 `medium`。

maxrate 还有一张保底表，单位 kbps：高度 ≥1600 为 12000，≥1080 为 4500，≥720 为 2200，≥360 为 800，更低为 400。算法是先按分辨率把源码率打折，如果打折后低于保底、而源自己也低于保底，就用源码率，不会把上限抬得比源还高。

`MaxrateUseSource` 这条路径对 HEVC、AV1、VP9 会走 `MaxrateForBrowserRemux`：大约源码率的 1.7 倍，再受保底和 3 倍源码率硬顶约束。H.264 可直出的源才更接近「用源码率做顶」。

### 5.5 分辨率阶梯

配置里常见 `360, 720, 1080, 2160`。目标不会比源真实像素高度更高。滤镜是 `scale=-2:高度`：按阶梯设高度，宽度按比例取偶数，适配这里使用的 H.264 编码参数。`-2` 是 ffmpeg 的「保持比例、自动取偶数宽度」。源本身那一档用 `null` 滤镜，保留真实像素，只重新编码，不缩放。

高码率的判定：分辨率已经是「1080p 高清」或「4k 超高清」，并且码率大于阈值。阈值配置 ≤0 时代码默认 10000 kbps；示例 yaml 是 8000。720p 的源永远不算高码率。

### 5.6 ffprobe 在本项目里读什么

```text
ffprobe -v error -show_streams -show_format -of json <文件>
```

真正用到的字段：第一条视频流的宽、高、codec、profile、pix_fmt、level；时长（视频流没有就用容器的，截成整数秒）；第一条音频的 codec 和 profile；容器名；`major_brand` / `compatible_brands`；大小；码率。没有视频流直接当错误，后面的视频流忽略。

### 5.7 用两份源片检验规则

假设开启 MP4 和 DASH，阶梯配置为 360/720/1080/2160，阈值为 8000 kbps：

| 源片 | 探测后的判断 | MP4 计划 | DASH 计划 |
|---|---|---|---|
| 1280×720、H.264/AAC-LC、兼容 MP4、4000 kbps | 能直出，不是高码率 | 原源保留为 720 档，只补 360 档 | 360、720 两档 |
| 1280×720、HEVC/AAC-LC、兼容 MP4、4000 kbps | HEVC 不满足浏览器直出规则 | 720 原尺寸规范化为 H.264 MP4，再补 360 档；成功后替换源资源 URL 并尝试删除旧源 | 360、720 两档 |

这里的“720 档”是产品清晰度标签，“1280×720”是实际像素，“4000 kbps”是源平均码率；三个量不是同一个概念。`PlanPipelines` 先用真实高度筛掉上采样档，再给 DASH 补最高适用档。画图时先分清“源资源行”和“派生资源行”，否则容易把同一高度的源片和派生片数重。

## 6. DASH、HLS、m3u8：这个项目到底产出什么

**本项目不产出 HLS，也不写 `.m3u8`。** 它产出两类东西：

1. 多档渐进 MP4 直链。
2. 一套 DASH：一个 `manifest.mpd`，外加每个清晰度一个 MP4。

数据库字段注释里写了「mp4, m3u8 等」，那只是注释。**新生成的 MP4/DASH 产物**落库 `format` 为 `mp4` 或 `dash`；上传源资源行经 ffprobe 归一化，可能保留 `matroska` 等源容器格式。`.m3u8` 和 `.ts` 只出现在两个兼容角落：合并上传时猜 Content-Type，以及给已经是绝对地址的历史 URL 补 `response-content-type`。`.mpd` 不在这个补查询串的 switch 里。

### 6.1 如果面试官问 m3u8 是什么

HLS 是苹果的自适应协议。一个主 `.m3u8` 列出若干档，每一档自己又是一个 `.m3u8`，里面是一串几秒一片的 `.ts` 或 fMP4。播放器播完一片就看网速，决定下一片从哪一档拿。

你要补一句：**当前实现选择 DASH**，FFmpeg 原生生成 SegmentTemplate / SegmentTimeline，初始化文件和媒体分片独立存储。直接编码和分块 copy 封装都使用这一格式；当前已不使用 `-single_file 1` 的单文件字节范围打包。仓库没有 HLS 与 DASH 的压测或兼容性对比，不能把它说成经实测证明 DASH 在所有浏览器更优。前端需要能处理 DASH 的播放器，纯 `<video src="manifest.mpd">` 不是通用播放方案。

| 维度 | 渐进 MP4 | 本项目 DASH | HLS（概念对照，项目未产出） |
|---|---|---|---|
| 入口 | 单个 `.mp4` URL | `.mpd` 清单 | `.m3u8` 清单 |
| 清晰度切换 | 用户换文件 URL | 播放器按段选 Representation | 播放器按段选变体流 |
| 本项目的媒体对象 | 每档一个 MP4 | 一个 MPD + 各 Representation 的初始化 MP4 和多段 .m4s | 无 |
| 访问关键点 | faststart、HTTP Range | MPD 中的相对模板、初始化文件与分片可达、时间轴正确 | 清单和媒体片段可达 |

### 6.2 DASH 在本项目里的每个词

| 词 | 在这里是什么 |
|---|---|
| MPD | `manifest.mpd`，XML 清单。库里一行资源，`resolution` 字面量是 `自适应`，`format=dash`，`codec=h264`，`bitrate=0` |
| Period | 一段时间轴。校验器和后台解析都遍历 Period |
| AdaptationSet | 同一类可切换流。视频一套，有音轨时音频再一套。参数是 `-adaptation_sets "id=0,streams=v id=1,streams=a"` |
| Representation | 某一档媒体流，初始化文件 `<hash>-init-stream<编号>.mp4`，媒体分片 `<hash>-stream<编号>-<五位序号>.m4s`。编号来自 FFmpeg 的 `$RepresentationID$`，媒体序号来自 `$Number%05d$`，不是 Go 里的 `dash:1080:high` |
| 分片时长 | 默认目标 4 秒，`-seg_duration 4`。每个视频流分别设置 `-force_key_frames:v:<编号> expr:gte(t,n_forced*4)`，NVENC 再设置 `-forced-idr:v:<编号> 1`。实际 GOP、音频和尾段时长以 SegmentTimeline 为准 |
| SegmentTemplate / SegmentTimeline | `-use_template 1 -use_timeline 1` 让 FFmpeg 直接记录真实时间轴，`-init_seg_name` / `-media_seg_name` 使用确定性的相对文件名。校验器只读检查静态点播清单、时间轴覆盖、全部引用文件和媒体时长，不改写 MPD；保留对旧单文件清单的兼容检查 |

DASH 的阶梯和 MP4 不完全一样。DASH 会保证包含「不超过源高度的最高标准档」：源不到 360 就用真实高度，不到 720 顶到 360，不到 1080 顶到 720，不到 2160 顶到 1080，否则 2160。超宽但被宽度判成 4K 的片子，标签可以是 2160，滤镜仍用 `null` 保持真实像素。

直接跑 DASH 时，即使开了 GPU，缩放也在 CPU 上做。注释写得很清楚：dash muxer 要的是 CPU 侧的帧，所以只加 `-hwaccel cuda`，不加 `-hwaccel_output_format cuda`。分段编码的 DASH 才可能用 `scale_cuda`。

上传顺序是先传各档 MP4，最后传 `manifest.mpd`。所以「清单已经在对象存储里」就可以当作各档都传完了，断点续传靠这个判断跳过。

## 7. 从用户按下上传到能播放

### 7.1 分片上传，不是一个大 body

| 方法 | 路径 |
|---|---|
| POST | `/v1/common/video/upload/chunk` |
| GET | `/v1/common/video/upload/status` |
| POST | `/v1/common/video/upload/complete` |

客户端按 `fileHash` + `index`（从 0 起）传每一片。MinIO 上是 `chunks/<hash>/<index>.part`，本地是 `chunkDir/<hash>/<index>.part`，先写临时文件再 rename。状态接口如果发现合并后的源对象已经在，就是秒传。

上传并非只由客户端控制：普通用户按北京时间自然日和不同 `fileHash` 占额（默认 10 个），同日同哈希重试不重复计数；管理员豁免。首片前占额、确认秒传前占额，complete 与投稿还会兜底；失败或放弃不退。Redis 哈希锁协调上传、合并、投稿与后台清理，避免同一对象刚验证完就被删除。Cron 每 5 分钟清理过期分片和未被资源引用的源对象，默认阈值分别为 2 小时和 1 小时。限额、锁和清理的细节见[上传用例](../../internal/application/video/upload_service.go)、[配额脚本](../../internal/infrastructure/cache/video/upload_quota.go)与[清理用例](../../internal/application/video/upload_cleanup.go)。

这里的 `fileHash` 在服务端主要是上传目录/对象的标识。合并前检查分片数与 `0..N-1` 索引完整性，当前合并流程没有对最终文件重新计算并比对内容哈希；“秒传”依赖同标识的完成对象存在。若面试官追问强校验，要明确区分“分片完整”与“字节内容等于客户端声称的 hash”。

合并：MinIO 优先服务端 `ComposeObject`。非最后一片小于 5 MiB 时 Compose 会失败，退回自己流式 `PutObject`。最终对象名永远是 `_source_<hash>.mp4`，不管用户原来的扩展名。本地则是把 `0.part … N-1.part` 拼进 `videos/<hash>/_source_<hash>.mp4`。返回给前端的是根相对路径，例如 `/user_files/<hash>/_source_<hash>.mp4` 或 `/uploads/videos/<hash>/_source_<hash>.mp4`。

示例配置：单片建议 10MB，上限 20MB，文件上限 7000MB，同时上传数 10。

### 7.2 发布先提交元数据，再异步投递转码

`PublishVideo` 先验证“这个 hash 已经完成合并”，在一次数据库事务里写视频、标签关系、分 P、**初始源资源行**；然后用脱离请求的任务异步投递 Kafka，并在投递成功后尽力把 Redis 进度写成 `queued`。投稿接口返回成功表示元数据已入库，**不表示 Kafka 已收到任务、FFmpeg 已成功或所有码率都可播**。后续 `ffprobe` 才会把源片的真实时长、格式、分辨率等补到资源行。Kafka 逻辑名是 `transcode`，示例里的物理 topic 是 `video_transcode_tasks`。消息体字段：`resolution`、`storageType`、`sourcePath`、`outputPath`、`fileHash`、`fileName`、`videoId`、`videoPartId`；这些 json tag 是线上契约。

**一致性边界：** MySQL 提交和 Kafka 发送不是一个原子事务。异步投递失败只记日志，当前代码没有事务 Outbox 或扫描补投，因此可能出现“投稿成功、转码任务未入队”。面试时应主动指出，若要保障不漏任务，可在投稿事务内写 Outbox，再由独立投递器可靠发送并标记；这是改进建议，不是现状。

### 7.3 消费者

消费组示例是 `f-ccg-video-transcode-group`。每个分区的 claim 同步处理消息，worker 池默认 2（示例 yaml 是 4），限制的是**同时处理的转码任务数**；一条任务可同时跑 MP4、DASH 两条管线，不能直接把 worker 数当作 ffmpeg 进程数。单个消费组能同时处理的任务还受 topic 分区数约束。

`ProcessTask` 的阶段：准备源 → ffprobe → 补全投稿时已写入的初始源资源的媒体信息并失效详情缓存 → 按开关跑管线 → 清理。消费者并非初始源资源行的首次写入点。

源文件如果在本地就直接读。如果是 MinIO 的根相对路径，会拼成 `http(s)://endpoint/bucket/key` 再下载到检查点目录，断点时按大小复用。

### 7.4 两条管线并行，失败含义不同

`mp4Enable` 和 `dashEnable` 可以同时开。`executeConfiguredPipelines` 起最多两个 goroutine。

| MP4 开关 | DASH 开关 | 源的情况 | 实际工作 |
|---|---|---|---|
| 开 | 任意 | 任意 | MP4 阶梯（含必要时的源规范化），DASH 按开关 |
| 都关 | 都关 | 不能播，或高码率 | 只做一条规范化 MP4 |
| 都关 | 都关 | 已能播且不是高码率 | 不跑 ffmpeg |
| 关 | 开 | 任意 | 只跑 DASH |

这里“只跑 DASH”指不生成新的渐进 MP4；投稿事务写下的初始源资源行仍在。若源本身是 HEVC 等不满足直出规则，开启 DASH 而关闭 MP4 时，并不会额外生成一条浏览器兼容的源 MP4。故不能笼统地把“投稿成功”或“源资源行存在”当作“原生 MP4 一定能播”。

失败规则，建议背下来：

- MP4 失败 → 整单失败。
- DASH 失败，但已经有 MP4 目标 → 打警告，整单仍可成功。
- 只有 DASH、没有 MP4 目标时 DASH 失败 → 整单失败。
- MP4 后来失败时，已经传上去的 DASH 不会回滚。

两条管线共用同一源文件，但各自编码、上传、落库；不在一个跨 MySQL 与对象存储的事务里。“MP4 失败即整单失败”是任务状态规则，不表示会撤销已完成的 DASH 文件或资源行。看详情资源列表与看 Kafka 任务是否成功，是两个不同问题。

MP4 成片名字：`_normalized_<hash>.mp4`、`<hash>_1080p_high.mp4`（高码率额外档，VIP）、`<hash>_1080p.mp4`、`<hash>_<高度>p.mp4`。高度 ≥1600 或等于 2160 的阶梯标成 VIP。DASH 只占库里的一行，URL 指向 `.../dash/manifest.mpd`。

成片时长必须和源相差不超过 2% 或至少 3 秒，否则这路输出作废。

### 7.5 为什么先落盘再上传

旧实现让 ffmpeg 多路输出写到本地 TCP，Go 边收边 multipart 上传。ffmpeg 的多输出要求每一路都及时被读走。任一路上传卡住，TCP 窗口塞满，整棵滤镜图停住，CPU 接近 0，进度永远不动。现在编码和对象存储解耦：ffmpeg 写完本地文件，进程退出，再串行上传。

### 7.6 长视频怎么分段

默认每段 180 秒，最短 60 秒，并且向上取整到 DASH 分片时长的倍数（默认 4 秒）。片长不足两段就不分段。最后一段不写 `-t`，避免 ffprobe 把小数秒截掉后丢掉尾巴。

音频不放进视频段里，整条音轨单独编成 `audio.m4a`，最后 `-c copy` 混进去。这样不会在段边界产生 AAC 爆音。MP4 段不强制关键帧；DASH 段按配置的分片网格强制关键帧（默认 4 秒），NVENC 强制 IDR，后面才能 copy 进 DASH muxer 并由其生成真实时间轴。

GPU 段和 CPU 段分目录放（`mp4-chunk-gpu-0000` 和 `mp4-chunk-cpu-0000`）。参数集不同，绝不能拼在一起。

### 7.7 GPU 失败会怎样

`GpuMode` 开着且没在冷却期，就先 `h264_nvenc`。成功就结束。上下文已取消就不再试 CPU。否则记一次 GPU 失败，再用 `libx264`。

冷却是进程内的：错误文本里有 cuda、nvenc、没有可用设备、设备忙、被信号杀掉，冷却 10 分钟。如果还提到驱动版本不匹配，冷却 6 小时。冷却期内新任务直接走 CPU。

回退时不再读 `CpuMode`。配置校验只禁止两个开关都关。只开 GPU 时，NVENC 失败仍会打日志并跑 libx264。

### 7.8 两套时钟，防止「看起来还在转」

编码墙钟：GPU 大约片长的 6 倍，CPU 大约 20 倍；目标超过 2 路再加时间；再按源体积加分钟。夹在 15 分钟到 12 小时。

停滞看门狗：无进度时间上限是 `片长秒数 / 3`，再夹到 **20 分钟～90 分钟**。进度来自 ffmpeg 的 `-progress pipe:2`，解析 `out_time_ms`、`out_time_us`、`out_time=`。任何一次进度回调都会刷新看门狗。

上传超时按 512 KiB/s 估算再加 2 分钟，夹在 3 分钟到 2 小时。这是截止时间，不是限速。

### 7.9 断点续传三层

检查点目录默认在临时目录的 `transcode-checkpoints`，任务子目录 `v<videoId>_p<partId>_<hash 前 16 位>`。关掉检查点就变成一次性临时目录，并且不分段。

| 层 | 依据 | 重试时 |
|---|---|---|
| L1 | MySQL 里的 URL 已经是目标相对路径，且对象大小 > 0 | 编码、上传、插入都跳过 |
| L2 | 检查点里已经有 probe 过的成片 | 跳过编码，重新上传 |
| 分段 | 某一段文件非空 | 只补缺的段 |
| 都没有 | | 重新 ffmpeg |

提交协议是：写到 `*-attempt-*`，probe 和时长校验通过后 `rename` 到正式名字。rename 成功才算完成。崩溃留在 attempt 目录里的半成品不会被复用。成功、视频被硬删、永久失败都会删检查点。可重试的失败保留检查点。启动时以及每 12 小时，删掉修改时间超过 7 天的检查点。

### 7.10 删视频时怎么停掉 ffmpeg

`CancelService` 在本进程取消对应任务，并向 `transcode:cancel:events` 广播 `{videoIds, requestedAt}`。别的实例的订阅者同样取消。这种删除会标记 Kafka offset，清掉 Redis 进度，删检查点，并尽量删掉已经传上去的 MP4 或 `dash/` 前缀。rebalance 或进程退出造成的取消不标记 offset，检查点留着，下次接着跑。

### 7.11 Kafka 失败后会不会丢、会不会重复

生产者 `WaitForAll`，重试 5 次。消息没有 key。

消费者默认自动提交是开的，但只有 `MarkMessage` 之后才会提交。处理成功会标记；永久错误（坏 JSON、缺字段、没有转码配置）先成功写 DLQ，再标记。DLQ 主题优先 `topics.dlq`，其次 `transcode_dlq`，否则 `<topic>.dlq`。示例是 `video_transcode_tasks.dlq`。

可重试错误在进程内再试 3 次（一共 4 次调用），间隔 500ms、1s、1.5s。仍失败就不标记，当前分区的 claim 结束；后续会话从未提交位置重新消费，因而可能重投。检查点使已提交的编码产物或已落库且对象仍存在的目标尽量跳过，不等于业务严格只执行一次。视频已被硬删则标记 offset，不再重试。

答“会不会丢”时分两个窗口：**入队前**，MySQL 已提交但异步投递 Kafka 失败有漏任务风险（见 7.2）；**入队后**，消费完成前不标记 offset，会重投并依赖确定性对象名、资源查验和检查点做幂等。DLQ 发送失败也不会标记原消息。

rebalance 超时默认 4 小时，因为一条转码可能很长，不能用默认的几十秒把消费者踢出组。

## 8. 播放器最终拿到什么

公开详情的每条资源大致是：`resolution`、`fileUrl`、`format`、`codec`、`bitrate`、`isSource`、`isVip`。

`自适应` 的排序权重是 100000，所以服务端把它排在首位，可供前端作为默认项。根据接口契约，播放器可以这样选择：

- `format === "dash"`：把 `fileUrl` 交给 dash.js，不要改查询串。
- `format === "mp4"`：原生 `<video src>`，浏览器自己发 Range。

管理端详情会再 HTTP GET 那个 mpd（超时 8 秒，最大 8 MiB），解析出每一档的 variants 给后台看。公开详情不展开。解析失败不影响播放地址本身。

详情元数据缓存 5 分钟。初始源资源在投稿事务里已保存；消费者在 ffprobe 后补全媒体信息，在整个管线收尾时失效详情缓存并抬高 generation，避免旧详情长期挡住新增资源；并不是每个 FFmpeg 子步骤完成都立即刷新一次公开详情。

播放排障按顺序查：`video_resources` 或分 P 资源行是否有正确的 `format/fileUrl` → URL 对应对象是否存在且返回正确 Content-Type → MP4 是否能处理 Range，或 MPD 的 SegmentTemplate 引用的初始化文件、媒体分片是否可访问（旧单文件产物检查 BaseURL） → 浏览器实际是否加载对应播放组件。只查到“FFmpeg 退出码为 0”不能证明用户能播放。

## 9. 搜索为什么看起来「几乎实时」

River 用 go-mysql/canal 订 binlog。示例配置订阅 `videos`、`users`、`tags`、`video_tags`、`user_focus`，但真正写进 ES 的规则只有视频和用户。标签表和视频标签表的变更会反查受影响的视频，重写 `search_videos` 文档，而不是把桥表本身当搜索文档。

位点存在 `runtime/river/master.info`（binlog 文件名和偏移），先把 ES bulk 写成功再记位点。批量默认 128 条或 200ms。要求 `binlog_row_image=FULL`。

关键词索引和向量索引是两套：

- `search_videos` / `search_users`：IK + 拼音，由 River 和 `-es` 的 mapping 文件维护。
- `search_videos_vector`：`dense_vector`，默认 2048 维，余弦相似度。由 Eino 的方舟 embedding 写入，River 不碰它。查询时向量召回和关键词召回做 RRF 融合，排名常数默认 60。

ES 挂了或没配，关键词搜索会退回 MySQL。这是降级，不是主路径。

用户改硬币、改经验导致的 `users.updated_at` 不会触发搜索文档重建，避免热更新把 ES 打爆。

## 10. 私信为什么在 Mongo

会话是两人一份，`_id` 直接用 `较小用户ID_较大用户ID`，不用自增。未读数、最后一条预览、是否还显示这个会话，都嵌在同一个文档里，一次更新就能完成。消息是追加写，按会话倒序翻页，适合文档和索引 `{conversationId:1, _id:-1}`。

跨进程把新消息推到在线连接，走的是 Redis 频道 `chat:user:{userID}`，不是 Mongo change stream。Mongo 没配时私信接口降级为不可用，HTTP 的其他功能还在。

## 11. AI 在架构里的位置

仓库里没有 AI 会话表，没有 Eino 的 compose 图，也没有按次扣硬币。代码不调用 xAI。请求里如果模型名带 `grok`，会被静默换成配置里的默认聊天模型。

三条客户端，不要说成「一个 AI SDK」：

| 能力 | 实际调用 |
|---|---|
| 聊天 | Eino 的 Claude ChatModel，协议是 Anthropic Messages。示例配置可以指到 DeepSeek 的 Anthropic 兼容地址。密钥是 `chatModelAPIKey`，没有全局 baseURL 兜底 |
| 生图 / 改图 | Eino 的方舟 `ImageGenerationModel`，密钥 `doubaoModelAPIKey` |
| 生视频、多模态向量 | 火山 Ark runtime SDK。代码注释写明 Eino 当时没有视频组件。`go.mod` 里的 eino embedding / es8 indexer 没有被任何 Go 文件 import |

聊天的 HTTP 全是 SSE。`POST /v1/common/ai/responses` 和 `GET .../responses/stream` 都走流。代码里那个非流式 `CreateResponse` 没有路由在调用。正式回答最多 4096 token；找视频前的意图分析最多 256 token。历史由前端每次把 `input` 整段传来，服务端按 `historyMaxTurns`（默认 20）和 `historyMaxChars`（默认 24000 个字符）裁剪，并保证窗口以 user 消息开头。思考开关关着时强制关闭；开着时默认强度是 `high`。

找视频的顺序：先用最近对话做一次小模型分析，抽出 intent 和最多 6 个关键词；`find_video` 时用方舟多模态向量做 kNN，和同一索引上的关键词召回做 RRF；向量失败就退回 MySQL 的 `LIKE`；还没有就取最新已发布。候选默认最多 8 条，塞进系统提示，并要求模型原样抄 `/video/{id}` 这种路径，最多给用户 5 个链接。聊天里的图片不会当成视觉输入发给聊天模型，只会变成文本标记；最多留 3 个 URL，只有第一张参与向量。

素材代理 `GET /v1/common/ai/assets` 不登录，但只允许打到火山相关域名。图片和视频状态里的 URL 会改写成这个代理。视频创建接口的 URL 不改写。AI 路由上的请求超时是 90 秒，和配置里的 `timeoutSec` 不是同一个旋钮。

管理端 `POST /v1/admin/rbac/menu/generate` 用另一套系统提示词，根据中文标题和现有菜单表生成菜单字段，并校验 SVG 图标。

## 12. 一致性：哪些是准的，哪些是最终一致

| 数据 | 真相在哪 | 什么时候对齐 |
|---|---|---|
| 用户、视频元数据、关系、评论正文 | MySQL | 请求内事务 |
| 播放/点赞/投币/收藏/评论/弹幕计数 | Redis 热计数 | Cron 每 5 分钟刷回 `videos` |
| 评论点赞 | Redis set + list | Cron 每 30 秒刷回 `comment_likes` |
| 热门榜 | Redis ZSET | 互动时加分，每 10 分钟乘 0.97 |
| 搜索文档 | ES | binlog，秒级，失败则停住位点 |
| 向量 | 另一套 ES 索引 | 显式重建或写入，不跟 binlog |
| 转码进度 | Redis | 2 小时 / 终态 24 小时，可丢，不影响成片 |
| 私信未读 | Mongo 文档里的字段 | 发送时 `$inc` |

经验：登录 +10，点赞 +10，观看 +10，每枚硬币 +15。每天正向经验合计上限 60，扣经验不占额度。等级 1 到 6，门槛 0 / 1000 / 3000 / 6000 / 10000 / 20000。

硬币：每日登录 +1；作品被收藏，作者 +0.1；被投币，作者得到投币数的 10%。投币流水和经验流水都有可空的 `dedup_key`，和用户 ID 组成唯一索引，用来挡重复加。

## 13. 面试时怎么在白板上画

先画五个框，不要画十四个上下文：

```text
浏览器 --HTTPS/WS--> Gin 单体 --SQL--> MySQL --binlog--> River --> ES
                         |                         |
                         +--> Redis                +-->（向量索引另写）
                         |
                         +--> Kafka --> FFmpeg --> MinIO
                         |
                         +--> Mongo（只有私信）
                         |
                         +--> Eino（聊天/图/视频/向量）
```

然后补三句：

1. 默认转码和 River 随 HTTP 服务运行；转码已可用独立消费者入口部署，River 仍由 HTTP App 启动。
2. 播放入口为渐进 MP4 直链或 DASH MPD；后者还引用初始化文件和 .m4s 分片，项目没有产出 m3u8。
3. 计数和点赞是 Redis 加 Cron 回刷，搜索是 binlog，不要说成「所有写都同步双写 ES」。

如果他追问转码，再画第二张：分片合并 → Kafka → ffprobe → MP4 与 DASH 两个 goroutine → 本地成片 → 上传 → `video_resources` 一行或多行 → 删详情缓存。失败时 MP4 一票否决，DASH 在已有 MP4 时可以跳过。

## 14. 你主动承认的设计边界（显得你真的读过）

- 单体里跑 ffmpeg，CPU 和接口互抢。水平扩展时每个实例都会进同一个消费组，分区数决定并行上限，还要用取消广播避免删视频后别的机器继续转。
- 投稿事务与异步 Kafka 投递之间没有 Outbox；转码幂等与断点续传解决的是重投，不能补足投递前的漏任务窗口。
- MP4/DASH 在本地写完才上传，需要足够临时磁盘空间；检查点便于重试，但运行中大视频会占盘，清扫只处理过期目录。
- DASH 清单最后上传并用相对文件名引用 Representation。若迁移或代理只搬走 `manifest.mpd`，或不能处理 Range，清单能取到也可能无法播放。
- 初始源资源在投稿事务里就存在；源为 HEVC 等格式时，要等规范化 MP4 或 DASH 产物完成才能按浏览器兼容路径播放。只开 DASH 不会顺带规范化源 MP4。
- 没有 JWT 黑名单；封禁后的 Redis 写穿通常缩短可见延迟，写穿失败可能受 60 秒缓存 TTL 影响。永久封禁与临时封禁的中间件覆盖范围不同。
- `is_souce_video` 这个列名拼错了，当作外部契约保留。
- `danmu:online:` 常量名叫 ZSet，实际是 Set。
- 向量索引和关键词索引会短暂不一致，因为它们不是同一条同步链路。
- AI 对话没有服务端会话库，刷新页面后的历史取决于前端是否把消息再传回来。

## 15. 媒体链路高频追问：按“结论—代码动作—边界”回答

**Q1：为什么投稿接口不等转码完再返回？**

结论：转码可能跑很久，不应占住一次 HTTP 请求。`PublishVideo` 在源文件已合并的前提下提交元数据与初始资源行，然后用后台任务投 Kafka；消费者另行执行 `ProcessTask`。边界是投稿成功只保证数据库那一步，当前没有 Outbox 保证后续投递一定发生。

**Q2：Kafka 消费是 exactly once 吗？**

不是。成功处理后才 `MarkMessage`，会话失效、进程退出或上传后落库前失败都可能重投。代码靠确定性产物路径、L1 资源与对象核验、L2 成片检查点、分段文件提交来减少重复工作；这些是幂等与恢复策略，不是跨 Kafka、MySQL、存储的原子提交。

**Q3：为什么 ffprobe 要读 codec/profile/pix_fmt，不能只看 `.mp4` 扩展名？**

扩展名只代表用户给的名字。`AssessBrowserPlayableSource` 还检查容器品牌、H.264 profile/level、像素格式、音轨编码。比如 HEVC 文件即使以 `.mp4` 命名，仍会被计划为需要浏览器兼容规范化；反之符合条件的 H.264 源可直接保留，少一次有损编码。

**Q4：为什么 720p 源不产 1080p？**

放大只增加像素数，不能补回源中没有的细节。`SelectResolutions` 只保留严格低于源真实像素高度的 MP4 阶梯，DASH 再补最高适用档；按宽度归为 4K 的超宽视频，其标签与真实高度分开，顶档用 `null` 保留实际像素。

**Q5：CRF 23、码率 4500 kbps，哪个控制最后文件大小？**

CRF 是质量目标，`-maxrate`/`-bufsize` 约束峰值，实际平均码率和文件大小仍取决于画面复杂度、音频及时长。库里的 `bitrate` 来自 ffprobe/文件估算，是产物观测值，不要把 `-maxrate` 说成恒定输出码率。HEVC 等高压缩源转 H.264 时，源码率也不宜机械当成新编码上限，代码有 `MaxrateForBrowserRemux` 预算。

**Q6：DASH 为什么一个 MPD 之外还有初始化 MP4 和 .m4s？为什么上传 MPD 最后？**

MPD 是索引，各 Representation 的初始化 MP4 提供解码配置，`.m4s` 提供分段媒体字节。SegmentTemplate 定义相对命名规则，SegmentTimeline 记录真实时间；应用不把它改写成固定段长。先传初始化文件和媒体分片，最后传清单，避免用户先拿到引用了缺失文件的清单；L1 续传仍用资源行与清单对象存在判断提交状态，这不能替代实际播放链路验证。

**Q7：DASH 失败，为什么任务有时还显示成功？**

`executeConfiguredPipelines` 会等两条 goroutine 结束。只要本次存在 MP4 目标且 MP4 成功，DASH 错误被记录后可跳过；若只有 DASH 目标，它失败就使整单失败。这个判定说明产品允许用渐进 MP4 兜底，但不代表失败的 DASH 文件已被事务回滚。

**Q8：转码卡住，靠什么发现？**

有总墙钟截止时间，也有进度停滞看门狗。FFmpeg 的 `-progress pipe:2` 报告 `out_time`；长时间没有进度就取消执行。上传另按文件大小计算截止时间。三个时钟对应“编码太慢”“编码不前进”“上传过久”，定位时先看进度阶段和错误原因，再看 ffmpeg stderr 与对象存储。

**Q9：GPU 机器不可用怎么办？**

启用 `GpuMode` 时先试 NVENC；失败且任务上下文仍有效则记录冷却并走 libx264。冷却状态在进程内，其他实例不会共享；CPU 回退路径不再检查 `CpuMode`。任务被删除或会话取消时不会继续做一次昂贵的 CPU 编码。

**Q10：为什么长片要分段，为什么音频单独处理？**

分段让重试只补未完成的块。块长按 DASH segment 网格对齐，已通过校验的块写入检查点。逐块 AAC 再拼接可能在边界产生缝隙/爆音，所以单独编码整条音轨，再与视频块合成。GPU 和 CPU 块分目录，防止回退后混拼不同编码参数的块。

**Q11：删视频时，其他实例已开始的 ffmpeg 会停吗？**

本机的任务登记器会取消上下文，并经 Redis 广播让其他实例的订阅器取消。因删除导致的任务作废会标记 offset、清进度和检查点，尽力清理已上传产物；rebalance 等导致的取消不标记，保留检查点等待重投。跨实例广播和清理都要按实际成功情况观察，不能把“尽力清理”讲成强事务。

**Q12：用户说 MPD 能打开但黑屏，先查什么？**

依次查 MPD 的 SegmentTemplate 相对路径、初始化文件与全部媒体分片是否可达、Content-Type 和浏览器播放器报错；旧单文件产物另查 BaseURL 与 Range 响应。`manifest.mpd` 只是入口；它可访问不证明媒体文件可访问。后台管理详情解析 variants 是诊断辅助，解析失败不会自动修好播放链路。

**Q13：现在怎样独立部署转码消费者，还缺什么？**

已有 `go run ./cmd/transcode-consumer -f config_dev.yaml`，复用 Kafka payload、转码管线、检查点、进度和 Redis 取消订阅；HTTP 节点设置 `transcode.localConsumerDisabled: true` 并重启后只投递、不消费。独立入口直接构造消费者，不受这个开关影响，只连接必要依赖。部署时对齐消费组、topic、可达 broker 地址和共享源存储，并按分区数与 worker 数估算容量。还需按需求补 Outbox 或可靠补投、独立健康监控和资源观测；已有独立进程不等于已经解决跨存储一致性。证据见 `cmd/transcode-consumer/main.go`、`bootstrap/providers_transcode.go` 和 `bootstrap/transcode_worker.go`。
