这份文档配合 [Archify 交互架构图](./diagrams/system-architecture.html) 使用。目标不是背一串技术名词，而是让你能回答：用户做了什么、后端按什么规则处理、数据究竟存在哪里、哪些步骤可以一起成功、哪些步骤会晚一点完成，以及出错后从哪里查。

全文以当前工作树源码为依据。**当前是一个按业务上下文组织的 Go 单体后端**，HTTP、WebSocket、River、Kafka 转码消费者和定时组件由同一个服务进程装配。图里的多个框不代表多个独立微服务。MySQL、Redis、MongoDB、Kafka、Elasticsearch 和存储系统是它使用的依赖；本地存储可以就是本机磁盘。

## 1. 小白先建立一个真实场景

假设小林上传一部 800 MB 的视频，标题叫“我的第一次 Go 项目”，选择技术分区和两个标签。这里的大小只是帮助理解的例子，不是项目上传限制。

小林实际提出了几种不同需求：

1. 把文件安全地传完，断网之后尽量接着传。
2. 建立一份作品，记住标题、作者、标签、分区和公开规则。
3. 把源文件处理成浏览器能播放的资源，必要时提供不同清晰度。
4. 让观众看到详情、找到播放地址，并能搜索到作品。
5. 给朋友发一句“我发布新视频了”，朋友在线时立即看到，离线后还能翻到历史。

这些需求的“成功”不是同一个成功。源文件传完，只代表仓库里有文件；作品入库，只代表目录里登记了作品；转码成功，代表媒体处理完成；搜索命中，代表搜索目录已有投影；私信推送到在线连接，又是另外一件事。

可以把系统想成一间视频工作室，但只把比喻当作入门工具：MySQL 是作品和业务关系的登记册，对象存储是放文件的仓库，Kafka 是交给加工人员的任务单，FFmpeg 是加工工具，ES 是方便检索的目录，Redis 是快速协作板，MongoDB 是私信历史和会话簿。登记册不会因为仓库收了一个文件就自动多出一份作品，任务单也不会因为写在内存里就自动进入 Kafka。后面的代码，就是把这些动作明确连接起来。

## 2. 打开交互图后，应该按什么顺序读

图里有五个引导主题，建议按编号读：①“上传与投稿”，找到浏览器、Gin 应用、MySQL 和存储，回答“文件在哪，作品在哪”；②“异步转码”，沿 Kafka 走到转码消费者和存储，回答“谁加工，为什么不用一直等”；③“搜索读模型”，沿 MySQL → River → ES，回答“为什么搜索可能晚一点”；④“缓存与私信”，弄清 Redis 与 MongoDB 的不同职责；⑤“面试：一致性边界”，用数据库提交后投递失败的例子，说明哪些事实已经成立，哪些保证仍需补充。

图上的实线、虚线和高亮用于强调主路径与异步边界。**线的样式本身不能证明事务、重试、幂等或可靠投递**，必须结合源码阅读。点击或切换视图的目的，是把暂时不关心的组件放到背景里；被淡化的组件仍然可能参与当前用例。

读每个框时，固定问三个问题：它干什么、它保存什么、它坏了会影响什么。读每根箭头时，再问三个问题：谁发起、发什么、失败会不会撤销前一步。第 5 节逐条解释图中连接，第 6 节把省略的连接补齐。

## 3. 三张“架构地图”不能混成一张

### 3.1 代码依赖图：回答“谁允许 import 谁”

接口层认识 HTTP 请求；应用层认识“投稿”这个用例；领域层认识“分区能不能投稿、初始状态是什么”；基础设施层认识 GORM、Redis、Kafka、FFmpeg；bootstrap 负责把它们装起来。

例如应用层要保存作品，就调用 `domain.VideoRepository` 这个接口。它不直接 import 基础设施包。GORM 仓储实现了这个接口，bootstrap 在启动构造时把实现传给应用服务。这叫依赖倒置：**业务代码提出需要的能力，技术代码来实现能力**。

代码依赖可以简写为：

```text
interfaces → application → domain
infrastructure → domain / application 中声明的端口
bootstrap → 各层，负责构造和绑定
```

这是模块之间的编译关系。所谓“依赖朝向业务核心”，不意味着请求不能调用数据库，也不意味着运行时只能顺着 import 方向走。

### 3.2 运行调用图：回答“一个动作实际经过谁”

小林点击投稿时，运行路径是：HTTP handler → `PublishService` → `VideoRepository.Persist` → GORM → MySQL。接口里装的是具体仓储对象，所以应用服务实际能调用基础设施实现，虽然应用层源码不需要 import 该实现所在的包。

把接口想成一个插座：应用层规定“我要能保存稿件的插座”；bootstrap 插入 MySQL 仓储这根线；运行时电流当然会通过实际插进去的线。换成 fake 仓储测试时，用例仍然可以运行。

### 3.3 部署图：回答“有几个进程、在哪些机器运行”

本项目的后端由 [main.go](../../cmd/server/main.go) 和 [App](../../internal/bootstrap/app.go) 装配。图上的 Gin 应用、River、转码消费者是不同职责，不是三个已经独立部署的后端服务。FFmpeg 是后台组件调用的外部工具进程；它不是业务微服务。

外部依赖可以本地部署，也可以连接远端，具体取决于配置和实际环境。单看此图不能推断有负载均衡、CDN、多可用区、数据库主从或自动扩容。当前仓库也没有提供可据此宣称的线上 QPS、故障恢复时间或吞吐量实测。

面试可以说：“我先分清代码边界、运行调用和进程部署。DDD 帮助组织业务和依赖，并没有自动把系统变成微服务。”

## 4. 每个组件为什么存在，哪些数据应以它为准

| 组件 | 用小林的例子解释 | 当前职责与事实边界 |
|---|---|---|
| 浏览器 / 管理端 | 发分片、填写标题；管理员审核作品 | 使用 HTTP 与 WebSocket。前端传来的 filePath、作者身份和成功标记不能直接代替服务端校验。 |
| Gin 应用 | 接收请求，再调用对应的业务用例 | 图中浓缩了路由、中间件、handler、application 和部分后台装配；不能把整个方框理解为“所有逻辑都写在 handler”。 |
| MySQL | 记住作品 ID、标题、作者、标签、分 P 和资源引用 | 主要业务记录与关系的权威来源。投稿多张表由一个 MySQL 事务保存；文件二进制不放在视频表里。 |
| MinIO / 本地存储 | 保存 800 MB 源文件和转出的 MP4、MPD 等产物 | 文件是否真实存在，以存储驱动的探测为依据。数据库里有 URL，不能证明 URL 对应文件还在。 |
| Kafka | 记录“请加工作品 123 的源文件” | 保存转码任务消息，并记录消费位置；它不替代作品表，也不保存完整视频内容。未进入 Kafka 的任务无法靠消费者重试找回来。 |
| 转码消费者 / FFmpeg | 按规则探测、编码、上传、登记可播放资源 | 消费者在同一后端进程里，由 worker 名额限制并发；FFmpeg/ffprobe 完成媒体操作。产物还需要存储和资源行配合，退出码 0 不等于观众已经能播。 |
| River | 看到 MySQL 的视频标题发生变化，更新搜索目录 | 基于 MySQL binlog 维护关键词读模型。记录 binlog 位点；默认示例配置可关闭它，启用与规则必须核实。 |
| Elasticsearch | 输入“第一次 Go”，快速找相关作品 | 关键词索引是业务数据的派生读模型；向量索引是另一条应用侧维护的路径。ES 返回结果不等于当前源文件已可播放。 |
| Redis | 快速计数、协调额度/锁、展示转码进度、广播在线消息 | Redis 不能统一称为“丢了也没事的缓存”。视频热计数、上传额度、调度与协调信息有不同后果；热计数尚未刷回 MySQL 时丢失，可能损失最新统计。 |
| MongoDB | 存“我发布新视频了”以及两人的会话、未读数 | 私信历史和会话状态在 Mongo 中。Redis Pub/Sub 负责通知在线连接，不承担离线消息历史。 |

“权威”要按数据类型说。例如作品标题主要看 MySQL，上传完成看实际源对象，详情热计数主要看 Redis，私信正文看 Mongo。不能用“所有真相都在 MySQL”覆盖整个项目。

更具体的数据结构在 [03 的存储选型](./03-基础设施与数据设计.md#1-为什么是这几样存储)、[Redis](./03-基础设施与数据设计.md#6-redis)、[MongoDB](./03-基础设施与数据设计.md#8-mongodb) 中。读这些表时先记住职责，再记字段。

## 5. 图里每根连接到底表示什么

以下按架构图的连接端点解释。标签文字可能随图的优化更直白，连接的业务含义以这里和源码为准。

| 连接 | 发起与内容 | 一句话读法 | 必须说清的边界 |
|---|---|---|---|
| 浏览器 → Gin 应用 | 浏览器发 HTTP 请求或建立 WS 连接 | “用户通过协议表达一个业务动作。” | HTTP 接口校验和 WS 消息校验各有入口；握手成功不等于每条消息都保存成功。 |
| Gin 应用 → MySQL | 用例经仓储保存/查询业务记录；投稿调用 `Persist` | “后端把作品登记进业务数据库。” | 图强调事务写入，实际还有读取；此事务不包含 Kafka、Redis、文件上传。 |
| MySQL → River | 已提交行变更进入 binlog，由 canal 订阅 | “登记册发生变化，搜索同步组件读到了变更记录。” | 不是每次 HTTP 请求直接调用 River；没有 source/rule 或没有启用，就不能推断同步已发生。 |
| River → ES | 构造文档、Bulk 批量写入，成功后保存位点 | “把变更转换成搜索目录。” | ES 成功但位点未保存时重启可能重放；写失败不能直接推进位点宣称处理完成。 |
| Gin 应用 → Redis | 缓存、额度、计数、调度、进度与实时事件等操作 | “后端借助快速存储和原子操作协调工作。” | 一个 Lua 脚本的原子性只覆盖那次 Redis 操作；它不会使 MySQL 和存储一起原子成功。 |
| Gin 应用 → MongoDB | 私信用例插入消息并更新会话 | “把私信和会话状态保存下来。” | `InsertMessage` 与 `ApplySend` 是先后两次调用，当前没有把两者包进一个 Mongo 跨文档事务。 |
| Gin 应用 → Kafka | 投稿 DB 提交后，detached 任务经端口发送转码消息 | “先登记作品，再安排异步加工。” | 后台任务在返回 HTTP 前被安排，可能在响应发出前或后开始；顺序保证是 DB 提交在先，不是响应必定在投递之前。没有 Outbox。 |
| Kafka → 转码消费者 | 消费组按分区拿任务，消费者获取 worker 名额并运行用例 | “加工人员领取待处理任务。” | 失败或会话结束可能重新投递。成功/删除任务会标记；永久坏消息需先成功进入 DLQ 再标记。Mark 不等于立即完成 broker 提交。 |
| 转码消费者 → 存储 | 处理管线把目标产物写入本地或 MinIO | “把处理完成的文件放回仓库。” | 仍需要资源落库、缓存失效与浏览器访问；上传与 MySQL 保存没有共同事务。 |

源码入口分别是 [投稿用例](../../internal/application/video/publish_service.go)、[投稿仓储](../../internal/infrastructure/persistence/video/publish_repo.go)、[River 同步](../../internal/infrastructure/river/sync.go)、[私信用例](../../internal/application/chat/chat_service.go)、[Kafka 消费](../../internal/infrastructure/mq/kafka_consumer.go) 和 [转码消费者](../../internal/infrastructure/mq/transcode_consumer.go)。你不需要一开始读完文件；先找到对应的方法，再问“它之前完成了什么，它失败后留下什么”。

## 6. 图中省略了什么，为什么这些省略很容易误导

概览图只保留主链路，省略连接是为了可读性。下面这些调用实际存在，不能把“图中没画”理解为“系统没做”。

| 应用 → 存储：写分片、合并源对象、查询是否完成 | 源文件先上传，之后才有投稿；并非只有转码消费者会写存储。 | [UploadService](../../internal/application/video/upload_service.go)、[存储实现](../../internal/infrastructure/storage) |

## 7. 链路一：从分片上传到投稿成功

### 7.1 文件先传完，作品随后登记

小林的浏览器先把大文件拆成多个分片，每次带文件哈希和分片编号。服务器做参数、分片大小和额度校验，把片段交给存储驱动。重新查询上传状态时，服务器检查已传分片以及最终源对象，浏览器可以补传缺失部分。

普通用户的上传额度按“北京时间自然日内不同源文件哈希”占用。同一哈希重复请求不会重复扣同一天额度；管理员免额度。秒传也要经过服务端额度检查。额度校验依赖 Redis 原子逻辑，Redis 出错时返回失败，不默许上传。见 [上传额度用例](../../internal/application/video/upload_quota.go) 和 [Redis 配额实现](../../internal/infrastructure/cache/video/upload_quota.go)。

合并时先查完整对象是否已存在；存在可以复用，否则核对分片集合并合并。文件哈希在此用作定位、去重和协调标识，不能仅凭客户端报了一个哈希就宣布完整文件已存在。`GetUploadStatus`、`CompleteUpload`、`ResolveCompletedUpload` 都有存储探测逻辑；内存完成缓存不是权威。见 [上传服务](../../internal/application/video/upload_service.go)。

完成上传返回源对象路径，仍没有自动生成 `videos` 行。文件和作品分开，才能允许小林先传完再填写标题，也允许多分 P 共用投稿流程；代价是上传后不投稿会留下待清理文件。

### 7.2 投稿时谁负责哪个问题

| 问题 | 当前放在哪里 | 为什么放这里 |
|---|---|---|
| 请求字段是否合法、登录者是谁 | HTTP 接口/中间件/handler | 这是协议与身份入口问题，不应该把 Gin 类型带到领域规则中。 |
| 源对象是否完成、上传与清理如何互斥 | `UploadService.WithPublishUploads` | 投稿需要存储和协调能力，不能只根据表单“已上传”判断。 |
| 私密、审核、定时如何决定稿件状态 | `domain.ResolvePublishVideoStatus` | 这是可以不连接数据库就测试的业务判断。 |
| 分区是否允许投稿、标签是否存在 | `PublishService` 查询，调用领域规则 | 应用层获取事实，领域层表达业务允许条件。 |
| 视频、标签关系、分 P、初始资源如何一起保存 | `VideoRepository.Persist` 的 MySQL 事务 | 多张相关表需要一起提交，具体 SQL/GORM 细节归仓储实现。 |
| 何时调度、同步向量、投递转码 | `PublishService` 事务后的 detached 任务 | 这些是跨组件编排，耗时动作不让投稿一直等待；失败语义必须单独讲。 |

### 7.3 一把锁解决的只是一个具体竞争

假设清理任务刚查出“这个源对象暂时无人引用”，恰好小林正在投稿。若投稿先验证对象存在，清理随后删掉对象，投稿最后成功写 DB，就会出现资源行指向已经消失的文件。

当前处理是在源验证到投稿入库期间持有源哈希的 Redis 锁，清理使用相同锁并核对 MySQL 引用。多哈希按序获取，减少相互等待。它针对上传/投稿/清理之间的协作竞争；锁有生命周期与失败处理，不能把它扩大成“所有跨库动作绝对安全”。有绕开锁的外部删除、存储故障等情况，仍会产生缺文件。见 [哈希锁](../../internal/infrastructure/cache/video/upload_guard.go) 和 [清理用例](../../internal/application/video/upload_cleanup.go)。

### 7.4 投稿响应成功究竟承诺什么

`PublishVideo` 在 `Persist` 成功后安排后台任务，随后返回作品 ID、业务状态等结果。**事务成功与后台投递是明确分开的两个阶段。** `tasks.Go` 已在函数返回前调用，后台 goroutine 可以立即开始；不能用“客户端已经收到响应之后才开始投递”描述严格时间顺序。

此时能确认的是同步校验通过、作品相关行已保存。不能确认的是 Kafka 已可靠接收任务、FFmpeg 已完成、关键词与向量索引已更新、所有播放器都能打开源文件。当前投递/调度失败只记录日志，不回滚已经提交的稿件，也没有 Outbox 把投递意图与稿件同事务保存。

## 8. 链路二：从转码任务到观众能播放

### 8.1 消息中放的是“加工说明”，不是整段视频

投稿通过应用端口进入 [TranscodeDispatchService](../../internal/application/media/dispatch_service.go)，再由 Kafka 实现投递任务。消息携带视频/分 P ID、源路径、哈希、目标路径、清晰度列表等加工信息。完整契约见 [03 的 Kafka](./03-基础设施与数据设计.md#7-kafka)。

消费者领取消息后获取 worker 名额，注册任务取消上下文和进度跟踪器，调用 `TranscodeService.ProcessTask`。worker 池限制进入加工阶段的任务数，防止无限制同时开 FFmpeg；它不自动规定每个任务所有子管线的 CPU 成本，也不是已实测的容量结论。

### 8.2 用“加工前、加工中、加工后”理解转码

加工前：校验消息、确认作品仍有效、解析存储类型、取源、探测视频。ffprobe 读到编码、分辨率、时长等真实信息，补到资源记录中。对象叫 `.mp4` 不表示里面必然是浏览器可直接播放的 H.264/AAC。

加工中：按配置运行 MP4、DASH 等管线，利用检查点复用已完成单元；源片是否可直接输出、是否需要浏览器兼容重编码，要看媒体规则。开启与关闭某个管线会改变结果，不能说每个上传一定生成全部清晰度。具体参数与例子放在 [02 第 5～7 节](./02-架构与媒体原理.md#5-从零听懂视频文件)。

加工后：上传产物、写资源行、失效详情元数据缓存、处理源文件与检查点清理，再结束任务。源码在每个重要阶段检查任务是否仍有效，删除作品时可以取消加工。但这些动作横跨文件、DB 和 Redis，并不是“一次大事务”。

### 8.3 为什么消息会重复，又为什么重复不应该造成灾难

有一种正常故障顺序：FFmpeg 已做完，资源已经保存，消费者尚未把处理位置成功提交到 Kafka，进程崩溃。恢复后这条消息还会来。还有 rebalance：分区分配换了，旧会话结束，在途任务的确认可能没完成。当前转码任务上下文关联消费会话和进程停止，不能根据底层某条注释说转码必然不受 rebalance 取消影响。

当前依靠确定性目标路径、资源/对象核验、资源唯一约束和检查点减少重复工作。**幂等的目标是重复处理尽量收敛到同样结果，不是承诺每个内部步骤只运行一次。** 检查点主要帮助复用已完成编码/暂存，它不是 MySQL 与 Kafka 的共同事务，也不能恢复尚未入队的任务。

可重试错误在同次处理内最多再试 3 次，共 4 次调用；仍失败不标记，后续消费会话可能重投。永久坏消息先发送 DLQ，DLQ 成功后才标记；DLQ 失败时原消息也不标记。已删除任务可标记并跳过。`MarkMessage` 记录的是待提交位置，不能说调用瞬间已经永久保存消费位置。见 [消费通用逻辑](../../internal/infrastructure/mq/kafka_consumer.go) 和 [finishMessage](../../internal/infrastructure/mq/transcode_consumer.go)。

### 8.4 播放要再经过一条读链路

观众打开详情，`DetailService` 先考虑已发布元数据缓存，再读热计数；未命中回源查询，最后组合作者、资源和用户互动状态。普通观众看公开作品，作者本人有私密/待审/定时稿预览分支，管理员详情又有单独路径。不能把“公开接口”简单等同于“永远匿名只读已发布”。

元数据与计数不是同一缓存。元数据保存标题、状态、资源等；热计数保存播放量等频繁变化数字。元数据缓存使用 generation：回源前记版本，落缓存时只允许版本没变的旧请求写回。例如旧请求读到“无 DASH 资源”，转码期间缓存被失效并推进版本，旧请求就不能重新把旧列表填回来。见 [DetailService](../../internal/application/video/detail_service.go)。

详情给前端 `format` 和 `fileUrl`，播放器继续去取实际媒体。MP4 可以依赖 HTTP Range 按字节获取；DASH 先取 MPD，再按其中的 Representation 和范围获取媒体。项目主要讲 MP4/DASH，`m3u8` 是 HLS 常见播放列表，不能仅凭资源字段注释就说当前主线实现了完整 HLS 管线。

所以“能播”的证据链至少包括：作品对该观众可见 → 资源行字段正确 → URL 指向存在的对象 → MP4/MPD 及其媒体可访问 → 浏览器使用兼容的播放器和编码。转码成功只是其中一段。

## 9. 链路三：关键词搜索和向量搜索

### 9.1 为什么不让每次搜索都扫业务表

小林的标题可能要支持中文分词、拼音、标签、相关度和高亮。ES 的索引是为这些读法准备的“搜索目录”。MySQL 保存业务记录，ES 保存适合检索的投影。把两者分工，减少让主业务库承担复杂检索的压力；代价是索引维护、运维成本和同步延迟。

这就是“读模型”：同一个作品，业务库用关系表表达，搜索目录把标题、标签等组进一份文档。读写形状不同，不代表系统采用了事件溯源。这里没有“只保存所有领域事件，再由事件恢复整个作品”的模型。

### 9.2 建索引与查索引是两条方向不同的线

建索引：MySQL 提交 → binlog → River → ES Bulk → 保存 binlog 位点。顺序很重要：如果先保存位点再写 ES，写失败后重启就可能跳过没写进去的事件。当前先成功写 ES 再保存位点；若在这两步之间崩溃，会重放，固定文档 ID 的覆盖写有助于收敛。

查索引：浏览器 → 搜索 handler → `SearchService` → ES → 结果 DTO。ES 未配置或常见查询错误时可回退 MySQL，回退使用父上下文，避免 ES 的子超时一起把回退查询取消。`MultiSearch` 响应条数不符合契约属于例外，直接返回错误；不能概括为“ES 任何问题都一定被 MySQL 屏蔽”。命中记录缺作者名/创建时间时，还可能从 DB 补这些字段，这不等于全面重新校验所有命中的当前业务状态。见 [SearchService](../../internal/application/search/search_service.go)。

River 是否启用、source 订了哪张表、rule 对哪些表生效都要查配置。订阅了一张表不表示它一定会生成索引动作。示例配置默认关闭 River；更详细规则、位点和标签重建在 [03 的 River](./03-基础设施与数据设计.md#94-river-怎么同步)。

### 9.3 向量索引不是关键词索引的自动附件

关键词偏向“你写了什么词”，向量偏向“你想表达什么含义”。向量需要应用侧构建内容、调用 embedding 能力，再更新另一份 ES 索引。River 不会仅凭行变更自动完成向量生成。

因此作品可能关键词能搜到，向量还未更新；向量服务故障也不表示 MySQL 没有作品。讲 AI 找视频时，再查 [02 的 AI 调用路径](./02-架构与媒体原理.md#11-ai-在架构里的位置)，不要把所有能力说成一个 Eino 调用：当前聊天/图片使用 Eino 组件，视频生成和多模态向量使用 Ark runtime SDK。

## 10. 链路四：私信从发送到在线通知

小林发消息给朋友，WS Hub 调用 `chat.Service.SendMessage`。领域规则校验发送者、接收者、文本/媒体内容，应用用例查询关注关系与发送限制，生成两人的确定性会话 ID。消息先经 `InsertMessage` 写 Mongo，再经 `ApplySend` 更新会话最后一条预览、可见性和接收者未读数。成功返回后 Hub 发 ack，推到本实例的在线连接，并经 Redis 发布到其他实例的订阅连接。

这里要分清三个结果：**消息正文保存、会话摘要推进、在线通知送达**。Mongo 更新单个会话文档时的 `$inc` 可以原子增加未读，但不能使消息插入和会话更新两步共同原子成功。若插入成功而更新失败，客户端可能收到失败，历史里却已有消息；重试可能再插入一条。当前 `clientMsgId` 在 WS ack 中用于关联请求，没有因此形成数据库层的完整去重约束。见 [私信用例](../../internal/application/chat/chat_service.go)、[Mongo Store](../../internal/infrastructure/persistence/chat/store.go) 和 [Hub.handleSend](../../internal/interfaces/ws/chat/hub.go)。

Redis Pub/Sub 又是第三个边界：接收者离线没有订阅连接，Pub/Sub 不把事件永久排队到他下次上线。历史可由 Mongo 查询，不等于实时事件会自动重放。当前每个在线连接的发送缓冲也有容量，不能把“Publish 被调用”说成“对方一定已经看到了”。

关注关系查询失败时，该私信限额校验记录告警并放行；上传额度的 Redis 故障则拒绝。这提醒你：**不同业务选择的失败策略不同**，不能背一句“Redis 挂了全部降级”套到所有接口。

## 11. 五套状态分别回答五个问题

| 状态/事实 | 它回答什么 | 小林场景 | 不能据此推断什么 |
|---|---|---|---|
| 上传是否完成 | 是否存在可使用的完整源对象 | 分片已合并，探测到了源文件 | 作品已投稿、内容已过审、源格式可直接播放。 |
| 作品业务状态 | 谁可以看到作品，是否待审核/待定时 | 已发布、私密、已删除、待审、定时 | 已完成转码、ES 已有文档。 |
| 转码任务/管线进度 | 当前加工走到哪一步 | `queued/running/succeeded/failed`，各阶段与百分比 | 视频公开状态；进度消失也不表示产物消失。 |
| 资源与对象可用性 | 某档清晰度的地址、格式、文件是否可用 | 720p 的资源行与对象存在 | 所有其他档位都已完成，MPD 引用的所有媒体都正常。 |
| 搜索投影状态 | 当前检索目录有没有跟上 | 关键词文档存在，向量文档尚未更新 | DB 事实不存在、用户现在一定有权看。 |

作品状态的真实枚举是：1 已发布、2 私密、3 已删除、4 待人工审核、5 定时发布，见 [enum/video.go](../../internal/domain/shared/enum/video.go)。**没有一个作品 `VideoStatusTranscoding` 与这些状态混用。** 加工进度定义在 [media/progress.go](../../internal/domain/media/progress.go)，属于另一维。

举两个组合：作品待审且转码成功，是“文件准备好了，尚不公开”；作品已发布且转码运行中，是“公开规则允许展示，播放资源仍在加工”。没有审核且立即公开的投稿就可能出现后一种。公开视频详情不要求等待所有管线完成才建立作品，能否此刻播放还要看已有源/成片的兼容性与资源状态。

## 12. 一致性与事务：不要被“一个 transaction”骗到

### 12.1 MySQL 本地事务能兜住什么

一次投稿的作品行、标签关系、分 P 和初始源资源在同一个 MySQL 事务内落库，其中一步出错就返回错误并回滚这些 DB 写入。它解决的是“不要有作品没关联数据、或半份分 P 数据”的本地写入问题。

此前上传的文件不会随 MySQL 回滚自动删除，此前占用的 Redis 额度也不会因为此事务失败自动被撤销；Kafka 投递在事务之后，更不是其中一部分。源码中的 `Transaction(...)` 范围就是边界，不能因为调用都在一个 Go 函数里就认为它们是一个事务。

### 12.2 Redis 原子操作能兜住什么

Lua 在一次 Redis 操作中完成检查和修改，使同哈希重试不重复计数，并阻止同一用户的多个不同哈希并发绕过每日上限。generation 比对可以防止旧元数据覆盖新失效版本。分布式锁可以让遵循协议的投稿与清理互斥。

这些能力各解决一个局部竞争。Lua 不会参与 MySQL commit，锁不会替你回滚对象上传。Redis 自身的数据持久性也取决于部署设置；项目架构文档不能替实际环境承诺“Redis 永远不丢数据”。

### 12.3 入队前与入队后的故障不是同一个问题

| 时间窗 | 可能发生什么 | 当前能依赖什么 | 当前不能承诺什么 |
|---|---|---|---|
| DB 已提交，后台任务未运行/未发送成功 | 作品已存在，Kafka 没有任务 | 错误日志、人工诊断；后续需要按实际运维能力处理 | 没有 Outbox，不能保证自动补回所有漏投任务。 |
| Kafka 已接收，消费尚未成功 | 消费失败、进程退出、rebalance | 不标记失败消息、重试/重投、检查点 | 不能保证永不重复，不能保证自动纠正永久坏输入。 |
| 产物已上传，资源落库失败 | 仓库里有文件，详情里没有对应行 | 重试中的资源/对象核验，日志排查 | 对象存储和 MySQL 没有共同事务，不能说绝无孤儿对象。 |
| 成片落库，消费位置未提交 | 再次处理已经完成的任务 | 路径、唯一约束、对象核验与检查点 | 不保证每次重投所有内部步骤都零开销。 |

Outbox 是可以讨论的改进：在保存作品的同一 MySQL 事务里额外保存“待发送任务”，再由后台发布器重试发 Kafka 并记录结果；消费者仍要幂等。它缩小的是“DB 保存与投递意图之间”的漏洞，不会让 MySQL、Kafka、文件上传天然成为一个事务。**这是建议，不是当前实现。**

### 12.4 最终一致不等于“过一会儿一定好”

最终一致的意思是不同副本/投影允许暂时不同，并通过明确的同步机制尝试对齐。这里 River 维护关键词索引，Cron 刷回计数，应用任务维护向量。若同步停止、配置未启用、任务从未进入队列或外部对象被删除，“等五分钟”未必有帮助。

可靠的说明要同时交代：谁负责同步、何时重试、失败留下什么、如何发现积压、有没有已实现的修复入口。当前文档只能据已有机制讲，不能把希望中的告警、自动补偿或对账写成事实。

## 13. 八个故障推演：像读过代码的人那样排障

### 场景 A：投稿成功了，一直没有新清晰度

先查 MySQL 是否有作品与初始资源，再确认源对象存在。接着找 `dispatch transcode task failed` 日志，区分消息根本没入队与已经入队但未成功消费。之后查 topic/group、消费位置、worker 名额、任务错误和 DLQ，最后查资源表与产物。**不能第一句就说“Kafka 会重试，所以不会漏”**：消费者找不到没进 Kafka 的任务。

### 场景 B：查询上传状态说完成，投稿却失败

对照存储当前状态重新探测源对象，别只查内存缓存。源对象可能被清理、外部删除或驱动暂时不可访问。再查 hash、文件名、额度、哈希锁、分区与标签。完成上传和通过投稿业务条件是两次不同校验。

### 场景 C：FFmpeg 已成功，浏览器还是黑屏

查资源行 `format/fileUrl`，直接请求 URL 看是否存在、是否支持适当的 Range，检查 MPD 与其 BaseURL 所指文件。再看编码/音轨、Content-Type、浏览器实际加载组件，以及跨域等访问条件。最后看详情缓存是否还显示旧资源。不要只重启消费者，更不要仅凭文件扩展名判定编码兼容。

### 场景 D：MySQL 有新标题，搜索还是旧标题

先确认查询走的是关键词还是向量索引，再看 River enable、source、rule、binlog 访问与位点、Bulk 失败。关键词同步正确并不证明向量同步正确。ES 查询成功但结果旧，未必触发 MySQL fallback；该回退针对未配置或查询错误，不是“看起来旧就重建”。

### 场景 E：Redis 暂时不可用

拆开影响：上传额度可能拒绝、哈希协调可能失败、详情缓存/热计数会受影响、进度看板和实时广播会受影响，调度也要核对。若 MySQL 和对象正常，已完成文件不会仅因进度 key 消失而自动消失。不同用例的回源和失败策略各有代码，不能承诺“所有接口都安全回源”。

### 场景 F：转码到 80% 时消费者 rebalance

查看会话取消/任务取消日志与是否标记。当前任务上下文关联会话，旧持有者要停止；未提交的位置可能再次消费。确认检查点目录保留情况以及哪些编码单元已完成，再核验目标对象和资源。不能只看 80% 百分比来决定续跑，也不能把百分比解释为剩余时间精确占比。

### 场景 G：朋友在线没看到私信，历史里却有

Mongo 保存和 WS 推送是两回事。查 `SendMessage` 是否全部成功，再看本实例房间、连接状态、发送缓冲和 Redis Pub/Sub。若正文已插入但会话更新失败，可能有正文而摘要/未读不对；若持久化完成但推送丢失，可查询历史。重试发送前应考虑重复风险，而不是声称当前 `clientMsgId` 已经实现数据库去重。

### 场景 H：HTTP 正常，但后台已经不工作

`App.Start` 对部分后台启动失败记日志并继续 HTTP；监听成功不代表转码、River、Cron 全部正常。查看各组件启动日志与实际活动、积压/位点是否变化。若要加入健康检查，建议分别区分 HTTP 存活与关键能力就绪，这是改进方向；不能把完善的能力探针说成当前已实现。

## 14. 选型如何讲出取舍，而不是背优点

| 选择 | 当前项目得到什么 | 支付什么代价 | 面试中可讨论的替代/演进 |
|---|---|---|---|
| 模块化单体 + DDD 边界 | 一条链路本地可追，依赖和用例职责清楚，DB 事务相对直接 | 转码可能与 HTTP 抢 CPU/内存，共享部署生命周期 | 有测量证据证明资源干扰后，可先独立部署转码 worker；这是演进建议。 |
| MySQL 保存主要业务关系 | 能用关系约束与本地事务管理投稿等写入 | 不适合把视频二进制直接塞表，也不天然提供复杂相关性检索 | 简单低规模需求可以更多依靠 MySQL 查询，但应测延迟与查询成本。 |
| Kafka 承载转码任务 | 请求与耗时加工分开，消费位置支持恢复 | 维护 broker/group，处理重复、坏消息和漏投窗口 | 简单系统可用 DB 任务表；是否用 Kafka 要按持续吞吐、积压、运维能力判断。 |
| Redis 热数据与协调 | 快速读写、Lua 原子检查、Pub/Sub 广播 | 引入数据持久性、缓存版本、刷盘、锁超时等问题 | 限额可以放 DB 做约束，成本与并发模型不同；不要只说“Redis 更快”。 |
| ES + River | 中文检索与相关度，业务数据异步生成读模型 | 多维护一个系统，索引可能落后，位点和关联字段需处理 | 初期可 MySQL fallback；成熟场景可加强同步监控和重建流程。 |
| MongoDB 私信 | 消息追加与会话文档表达直接，按会话游标分页 | 消息与摘要两步一致性、索引及另一套运维 | MySQL 也能做私信；Mongo 的选择不意味着 MySQL 做不了或已经实测更慢。 |
| 本地 / MinIO 存储驱动 | 同一用例可切换文件落点，业务不直接认识 SDK | 路径解析、对象与资源的一致性；本地盘对多实例共享不友好 | 共享对象存储更适合多实例取同一源，但仍要验证权限、URL 与访问成本。 |

如果追问“为什么不用微服务”，可答：当前优先把业务边界和依赖整理清楚。微服务会增加网络超时、分布式一致性、部署和观测成本；已有边界是将来拆分的基础，但并不等于已经完成拆分。是否拆，应该先看 CPU 干扰、故障隔离、团队 ownership 和实际负载证据。

## 15. 面试表达：三分钟和深入版

### 15.1 三分钟版本：可以照着练，数字用自己的真实证据

> 这是一个 Go 视频站后端，我先强调它目前是按业务上下文组织的单体。Gin HTTP、WebSocket 和转码、搜索同步、定时任务由一个后端进程装配，外部连接 MySQL、Redis、Kafka、MongoDB、ES 和本地/MinIO 存储。
>
> 代码分成接口、应用、领域、基础设施和 bootstrap。接口接协议，应用编排用例，领域表达业务规则和仓储接口，基础设施实现 GORM、缓存、消息和媒体能力，bootstrap 做依赖绑定。这样 application 不需要直接依赖 Kafka 或 MySQL 的具体驱动，测试能注入 fake。
>
> 最核心的链路是上传和投稿。先把分片合并成源对象，服务端会核实对象存在并校验额度。投稿验证分区和标签，在源哈希锁保护下把作品、关系、分 P 和初始资源放到一个 MySQL 事务里。事务成功后安排后台任务投递 Kafka，HTTP 不等待整条转码。
>
> 消费者有 worker 池，调用 ffprobe 和 FFmpeg，再上传产物、写资源和刷新详情缓存。失败消息不直接确认，重投用检查点、资源和对象核验减少重复。永久坏消息成功送入死信后才确认。这里不是恰好一次，尤其 DB 已提交而 Kafka 尚未收到任务之间，当前没有 Outbox，存在漏投窗口。
>
> 详情组合 MySQL 读模型和 Redis 热计数；搜索是另一条读链路，MySQL binlog 经 River 异步写关键词索引，向量索引由应用维护。私信历史和会话存 Mongo，Redis Pub/Sub 通知在线连接。作品公开、转码成功、搜索可见是三个不同状态，我会按阶段分别判断和排障。

这段话只说源码能够支撑的能力。若是学习项目，可以说“我阅读、梳理并验证了这些链路”，不要把自己未实施的模块说成亲自从零建设，更不要编线上百万日活或压测数字。

### 15.2 深入版：选一条主线，回答五层问题

面试官继续问时，沿投稿展开，不要立刻换成十种中间件百科。

1. **业务层**：上传完成与作品公开为什么不同；分 P、审核和定时怎样影响状态。
2. **代码层**：handler → `PublishService` → 领域规则/端口 → 仓储实现；谁把实现注入进来。
3. **数据层**：哪些行在 MySQL 一起提交，源对象与热计数分别存哪。
4. **可靠性层**：DB → MQ 漏投窗、消费重投、对象与 DB 不一致、旧缓存回填。
5. **取舍层**：为什么现在保持单体；下一步先补投递可靠性还是拆服务，应该根据什么证据决定。

比如对“怎么保证一致性”的回答可以是：“投稿的相关业务行靠 MySQL 本地事务；上传与清理靠共享哈希锁协调；缓存回填靠 generation；Kafka 消费允许重投并核验产物。跨 MySQL 和 Kafka 当前没有 Outbox，因此我不能承诺可靠漏投补偿，若生产要求提升，优先把投递意图持久化并建立积压和失败的可观察性。”这比“用了事务和消息队列保证最终一致”更具体。

## 16. 高频追问：答案要包含结论、依据和边界

### 追问 1：DDD 是不是四个目录？

不是目录数量决定。这里按业务上下文组织，应用服务协调用例，领域表达可独立测试的业务规则与接口，技术实现通过端口注入。目录帮助落实边界，架构测试能检查部分 import 约束；并非每个上下文都有复杂聚合，也不能从目录断言实践了完整事件驱动 DDD。

### 追问 2：领域层不依赖基础设施，怎么保存数据？

领域定义所需的仓储接口，基础设施实现它，bootstrap 构造具体对象并注入应用服务。编译时应用只依赖接口，运行时接口调用实际落到 GORM 实现。找 `VideoRepository.Persist` 和 [bootstrap](../../internal/bootstrap) 就能把这件事串起来。

### 追问 3：把全部投稿逻辑放进数据库事务，问题不就解决了？

事务只能回滚同一数据库中的相关操作。FFmpeg、Redis、对象上传与 Kafka 不会被 GORM 的 rollback 撤销，而且长转码占着 DB 事务会增加锁和连接占用。当前把业务写入事务保持在 DB 范围内，耗时任务放后面，但必须正视后续投递失败窗口。

### 追问 4：Kafka 已经很可靠，为什么还需要 Outbox？

Kafka 可靠性主要讨论已经交给 Kafka 的消息。进程在 DB 提交后、发送前崩溃，Kafka 不知道存在待发任务。Outbox 把任务意图和业务行一起写 DB，再重试发送，解决这个间隙；当前没有实现，消费者幂等仍然必要。

### 追问 5：有幂等，是不是不会重复执行？

重复投递和重复执行可以发生。幂等是重复尝试不应不断产生新的业务结果或破坏已有结果。当前检查点和目标核验帮助复用已完成工作，唯一资源约束辅助收敛；需要分别看每个副作用，不能把一个检查点当成全链路恰好一次证明。

### 追问 6：缓存 generation 和 TTL 有什么区别？

TTL 限制缓存持续存在的时间，generation 解决在途旧请求晚到的问题。A 先读 DB 旧资源，B 转码完成并失效缓存，A 后写回；仅删除 key 可能被 A 重新填旧值。A 回源前记录代数，B 推进代数，A 比对不匹配就不能写。不能因此说 DB 和 Redis 成了事务，缓存操作本身仍可能失败。

### 追问 7：ES 故障是不是系统就完全不能搜索？

当前关键词搜索有 MySQL 回退，ES 未配置或常见查询失败可以用回退路径。回退的搜索能力和相关度不保证等同 ES，负载会转到 MySQL；契约错误有直接报错分支。索引陈旧但请求成功不自动触发回退。

### 追问 8：用了 Mongo 的 `$inc`，私信是否就不丢不重？

`$inc` 原子地修改单个会话文档中的未读数，但消息插入与会话更新是两个操作；实时 WS 推送还是第三个边界。前一步成功后一步失败会留下中间状态，客户端重试可能重复。要提升保证，可以讨论事务、业务消息 ID 去重和对账/重放，但这些都是建议，不能说已经有。

### 追问 9：现在加两个实例是不是就能水平扩容？

不能从一个 Pub/Sub 或消费组推导所有组件都正确。Kafka 分区决定消费分配，本地源盘与检查点需要可访问，Cron/定时发布要检查重复执行，本地房间只持有本实例连接，配置与文件路径也要一致。先逐项明确共享状态和任务 ownership，再验证多实例行为。

### 追问 10：怎么证明架构的收益？

已有架构测试检查应用层不导入 infrastructure 等边界；用例构造函数允许注入 fake；投稿、缓存、消费和 River 有相应测试。它们支撑可测试性与依赖约束，不能直接证明高吞吐或所有外部系统的集成正确。若谈性能收益，需要补真实 workload、延迟分位、资源成本和对照实验。

### 追问 11：你最先改善哪一点？

可以选 DB 到 Kafka 的投递漏洞，理由是当前用户已经获得成功稿件却可能没有加工任务。建议 Outbox/任务持久化、可观测的投递状态、重试与对账，消费者继续幂等。若真实数据反而证明转码抢 CPU 导致接口延迟，优先拆 worker 或限制资源；先用证据排优先级，不按新技术热度决定。

## 17. 自测练习：先停下来想，再对答案

### 练习一：判断下面四句话

1. “作品已发布，所以全部清晰度已经生成。”
2. “DB 事务成功，但 Kafka 不可用，DB 会自动回滚。”
3. “消息保存进 Mongo，所以对方在线一定收到通知。”
4. “应用只依赖接口，所以运行时不会调用基础设施。”

**答案：四句都错。** 第一混淆作品业务状态与转码状态；第二超出了 MySQL 事务范围；第三混淆持久化与实时送达；第四混淆编译依赖和实际调用。能用各自的源码入口解释错误，才算真正理解。

### 练习二：作品已入库，Kafka 完全没有任务，重启消费者能修好么？

**答案：不能据此承诺。** 消费者只读取已有消息；没投进去的任务要从业务状态/任务意图发现并补发。当前没有持久化 Outbox 承担这件事。先查异步投递日志与源/资源事实，若设计自动修复，要明确新增任务记录与对账机制，而不是假设现有重试已经覆盖。

### 练习三：A 读到旧详情，B 转码完成失效缓存，A 再写回，如何拦住？

**答案：回源前取得 generation，写缓存时 CAS 比对。** B 失效同时推进代数，A 带旧代数写入就失败。若 A 在读 DB 后才获取新代数，反而可能让旧内容拿着新版本成功回填，所以获取时间也重要。

### 练习四：清理对象与投稿并发，哪一个信息决定能不能删除？

**答案：完整判断要有协调和引用核查。** 清理与投稿使用同一哈希锁；清理检查 MySQL 资源引用，投稿在验证源到入库期间持锁。不能仅按创建时间决定删，也不能仅因进程内缓存标了完成就不查对象。

### 练习五：资源表有 720p URL，但存储里没有文件，谁错了？

**答案：首先说明这是跨系统不一致，不能单凭一处决定原因。** 可能是外部删除、上传/落库时序错误或路径配置问题。检查该档资源与目标对象、转码日志和存储解析。业务记录证明曾登记资源，实际对象探测证明此刻字节是否存在，两个事实缺一不可。

### 练习六：只有十分钟白板时间，怎么画和讲？

**答案：** 先画浏览器 → 应用 → MySQL；补应用 → 存储表示上传，补应用 → Kafka → worker → 存储/DB 表示加工；补 MySQL → River → ES，再补应用 → ES 表示查询；旁边放 Redis 与 Mongo。圈出同一后端进程中的应用、worker、River，标注“DB 本地事务”“无 Outbox”“重投需幂等”“索引异步”。最后选一次投稿，把状态分开并讲一个失败窗口。完整白板技巧见 [02 第 13 节](./02-架构与媒体原理.md#13-面试时怎么在白板上画)。
