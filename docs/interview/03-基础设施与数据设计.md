# 基础设施与数据设计

这份文档先讲数据为何这样流动，再列可核对的表、Key、索引和配置。面试时建议按「权威数据在哪里 → 写入顺序 → 异步传播 → 失败后怎样恢复 → 哪些问题仍未解决」回答，而不是背中间件清单。列名来自 `internal/infrastructure/persistence/po` 的 GORM tag。没有 `column:` 时，列名是 GORM 的蛇形：`UserID` → `user_id`，`IP` → `ip`，`URL` → `url`。

生产迁移在 `migration.Migrator.AutoMigrate`。一共 **36 个 GORM 模型 + 1 张没有 struct 的 `video_tags`**，合计 37 张表。连接上关了外键（`DisableForeignKeyConstraintWhenMigrating: true`），下面的「关联」是 GORM 逻辑关系，库里没有 FOREIGN KEY。

没有 `deleted_at`。视频删除是把 `videos.status` 改成 3。

多数表嵌入 `po.Model`，于是有 `id`（自增）、`created_at`、`updated_at`（`datetime(3)`，可为 NULL）。下面各表如果写「含 Model」，就是这三列，不再重复。

容易叫错的表名：`danmu` 不复数，`user_focus` 不复数，`casbin_rule` 不复数。`banners` 和 `user_confs` 没有 `TableName()`，靠 GORM 默认复数。

站点配置不在 MySQL 里，在 YAML（Viper，可热更新）：登录开关、验证码、存储分片大小、转码阶梯都在配置文件。

### 先建立一张数据流地图

| 场景 | 同步写入与权威位置 | 异步/派生数据 | 失败或延迟时的现象 |
|---|---|---|---|
| 视频投稿 | MySQL `videos` 状态、分 P 和初始源资源行在投稿事务中写入；转码产物后续另写资源行 | Kafka 转码、River 关键词索引、向量同步 | 投稿成功不保证 Kafka 已入队；已发布也不等于搜索索引和所有清晰度就绪，需分别看状态、资源、索引和进度 |
| 视频统计 | Redis 可用时的计数值；不可用时 MySQL 直写 | 5 分钟 Cron 回写 MySQL | DB 计数可能落后；Redis 写入结果不明时不能盲目重做增量 |
| 评论点赞 | Redis 的用户集合与最终意图队列 | 30 秒 Cron 写 `comment_likes`、评论计数 | Redis 成功而 DB 尚未更新是预期的短暂状态 |
| 私信 | Mongo 消息文档和会话文档 | Redis Pub/Sub 推 WebSocket | 消息持久化与会话摘要是两次写；Pub/Sub 只负责在线通知，离线靠 Mongo 查询 |
| 搜索 | MySQL 用户、视频、标签和关注关系 | River binlog → 关键词索引；应用 → 向量索引 | 两套索引各有延迟，不能把 ES 当交易真相 |

上表是读代码时的定位入口；每一行都要区分「接口成功」「持久化成功」和「派生状态可见」三个时点。

## 1. 为什么是这几样存储

| 存储 | 放什么 | 为什么不是别的 |
|---|---|---|
| MySQL | 用户、稿件、互动关系、权限、通知正文 | 要事务、唯一约束、按主键更新 |
| Redis | 热计数、缓存、榜单、验证码、进度、Pub/Sub | 适合原子增量与低延迟读写；其中热计数不能简单视作可丢缓存 |
| MongoDB | 只有私信会话和消息 | 两人一份会话，未读和最后一条嵌在同一个文档里 |
| Kafka | 只有转码任务 | 编码比 HTTP 慢几个数量级，要能重投、要有死信 |
| Elasticsearch | 关键词搜索；另一套索引放向量 | 中文分词、拼音、kNN 都不是 MySQL 的舒适区 |
| 对象存储 | 源片、MP4、mpd | 大文件不进数据库 |
| 本地检查点目录 | 转码断点 | 只活在转码机磁盘上，不进 MySQL |

这里的「权威」要按场景说：用户和视频实体以 MySQL 为准；视频热计数在 Redis 正常时以 Redis 为准；私信实体以 Mongo 为准。对象存储存文件，MySQL 资源行存引用，两者之间没有跨系统事务。ES 是可重建的读模型。没有物理外键并不代表没有关系约束：唯一索引挡重复关系，业务代码验证状态与归属；绕开业务代码直接写库时，仍可能产生孤儿行。

## 2. MySQL：身份

### `users`（含 Model）

| 列 | 类型要点 | 含义 |
|---|---|---|
| username | varchar(50) NOT NULL，唯一 | 登录名。视频作者用用户名关联，不是用户 ID |
| email | varchar(100) NOT NULL，唯一 | 邮箱 |
| password | varchar(255) NOT NULL | 密码哈希，JSON 不输出 |
| avatar | varchar(500) | 头像 |
| description | varchar(500) | 简介 |
| gender | 默认 0 | 0 未知，1 男，2 女 |
| birthday | 可空时间 | 生日 |
| level | 默认 1 | 1～6 |
| open_id | varchar(50)，空白会写成 NULL | 第三方 ID。空串不能入库 |
| register_source | varchar(50) | 注册来源 |
| exp | 默认 0 | 经验 |
| coin_count | decimal(10,1)，默认 0 | 硬币，一位小数 |
| status | 默认 1 | 1 正常，2 封禁，3 永久封禁 |
| current_role_id | 默认 0 | 当前角色 |
| register_ip / last_login_ip | varchar(20) | IP |
| register_addr / last_login_addr | varchar(200) | ip2region 解析出的地址 |

唯一索引 `uk_users_open_id_source (open_id, register_source)` 是迁移代码额外建的，不在 tag 里。MySQL 唯一索引允许多个 NULL，所以多个邮箱用户可以没有 open_id。不用函数索引，因为 River 用的 canal 解析不了函数索引 DDL。

钩子：

- `BeforeCreate` / `BeforeSave`：空白 `open_id` 写成 NULL。map 形式的部分更新只有这次真的在写 `open_id` 时才改。曾经无条件 `SetColumn`，结果改硬币会把 OAuth 绑定清掉。
- `AfterCreate`：同一事务插入 `user_confs`（默认横幅 ID 来自 context，缺省 19）和名为「默认收藏夹」的收藏夹。

`Videos` 关联用 `author_username` 对 `users.username`，不是 `user_id`。

这使作者名成为跨表关联键。面试若被问「为什么不存 user_id」，应如实说当前模型如此，不能宣称用户名可任意改动而无代价；改名必须考虑视频、搜索文档和其他用户名快照的同步。

### `user_confs`（无 Model，主键是 user_id）

| 列 | 含义 |
|---|---|
| user_id | 主键，同时 tag 里还有 unique |
| like_tags | JSON，喜欢的标签 |
| banner_id | 默认 0，主页横幅 ID |
| banner_url | varchar(500)，自定义横幅 |
| open_collect / open_fans / open_follow / open_like_video / open_coin_video | 是否公开，默认都是 true |

没有 `created_at`。单列整型主键会被 GORM 标成自增，这是驱动行为，业务上它应该等于 `users.id`。

### `user_ban_records`（含 Model）

user_id（索引）、status、reason varchar(500)、days、start_at、end_at 可空、operator_id、is_unbanned（默认 false，有索引）。

### `user_login_records`（含 Model）

user_id、ip varchar(45)、addr varchar(200)、user_agent varchar(255)、login_type varchar(20)，注释里的例子是 `pwd/qq`。user_id、ip、login_type 有索引。

### `user_exp_records`（含 Model）

user_id、delta（int64，可为负）、reason varchar(255)、dedup_key 可空 varchar(64)。唯一索引 `(user_id, dedup_key)`。NULL 的 dedup_key 不互相冲突，所以没有幂等键的流水可以有多条。

### `user_coin_records`（含 Model）

同上，delta 是 decimal(10,1)。唯一索引 `(user_id, dedup_key)`。

经验规则（代码常量，不在表里）：登录 +10，点赞 +10，观看 +10，每枚硬币 +15。每天正向合计上限 60。负向不占额度。等级门槛：2 级 1000，3 级 3000，4 级 6000，5 级 10000，6 级 20000，最高 6。

硬币规则：每日登录 +1；被收藏作者 +0.1；被投币作者得到枚数的 10%。

### `user_focus`（含 Model，表名不复数）

user_id、focus_user_id。唯一索引就是这两列。表示「谁关注了谁」。

## 3. MySQL：权限

Casbin 模型在 `conf/rbac_model.conf`：请求是 `sub, obj, act`，策略也是这三项，角色继承 `g`。效果是有一条 allow 就通过。匹配器是 `g(角色) && globMatch(路径) && (方法相同或策略方法是 *)`。所以策略可以写 `/v1/admin/**`。

默认角色名：普通用户、超级管理员、大会员。

**请求实际怎样鉴权：** HTTP 中间件把 JWT 解析出的 uid 转成 `user:<id>` 主体，用 Gin `FullPath()`（空时回退 URL 路径）与 HTTP 方法调用 Casbin `Enforce`。`g` 把这个主体绑定到角色名，也把角色名绑定到父角色名；`p` 才是角色名、接口路径、方法。`api_resources` 是供后台勾选的接口目录，`role_menus` 是前端菜单可见性，它们本身都不是中间件的放行判据。`users.current_role_id` 用于当前角色/菜单选择；`SwitchRole` 检查 `user_roles` 归属并更新该列，没有在切换时重写 Casbin 的 `g`。所以不能把「切换当前角色」解释为只按当前角色进行接口鉴权。

**边界：** `SyncedEnforcer` 提供进程内并发安全，代码加载策略并由管理操作修改策略；没有看到跨实例策略变更广播机制。多实例部署时应验证其他实例何时重载策略，不能直接保证修改后所有实例立即一致。

### `roles`（含 Model）

name varchar(50) 唯一，desc varchar(200)。`AfterDelete` 会删掉这个角色的 `role_menus` 和 `user_roles`。

### `menus`（含 Model）

title / title_en / title_ja、icon varchar(2048)（存 SVG）、path、name、component、keep_alive、parent_id 可空、sort_order。`children` 是 `gorm:"-"`，不入库。

### `user_roles`

复合主键 user_id + role_id。没有 Model，没有时间列。

### `role_menus`

复合主键 role_id + menu_id，另有 is_inherited，默认 false。角色继承来的菜单用这个标记，避免手改和继承打架。

### `api_resources`（含 Model）

path varchar(200)、method varchar(10)，二者联合唯一。summary varchar(200)。tags 是 JSON。`-rs` 会按真实路由表把接口同步进这张表，供后台勾权限。

### `casbin_rule`

id、ptype varchar(100)、v0～v5 varchar(100)。这是 Casbin 官方表结构。对本项目：ptype=`p` 时 v0 是角色、v1 是路径、v2 是方法；ptype=`g` 时 v0 是用户、v1 是角色。v3～v5 空着。

## 4. MySQL：视频

### 状态和枚举（先背这个）

`videos.status`：1 已发布，2 私密，3 已删除，4 待审核，5 定时发布。

清晰度字符串存在资源表里，不是数字：

| 常量 | 库里的字面量 |
|---|---|
| 360 | `360p 流畅` |
| 720 | `720p 准高清` |
| 1080 | `1080p 高清` |
| 1080 高码率 | `1080p 高码率` |
| 2160 | `4k 超高清` |
| DASH | `自适应` |

存储类型也是中文字符串：`本地`、`Minio`、`七牛云Kodo`、`腾讯云COS`、`阿里云OSS`。tag 上的 `default:1` 不要背，以这五个常量为准。

### `video_partitions`（含 Model）

name varchar(50)、icon text（SVG）、sort_order 默认 1、is_active 默认 true、is_submittable 默认 true。后两个有索引。种子数据来自 `init_resource/sql/video_partitions.sql`，CLI `-vp` 导入。

### `videos`（含 Model）

| 列 | 要点 |
|---|---|
| title | varchar(200) NOT NULL，有索引 |
| description | text |
| cover | varchar(500) |
| duration | 秒，NOT NULL 默认 0。转码 probe 之后回写 |
| author_username | varchar(50) NOT NULL。单列索引，并和 status 组成 `idx_videos_author_status` |
| partition_id | NOT NULL，索引 |
| views / likes / comment_count / coin_count / favorite_count / danmu_count | 默认 0。热路径在 Redis，Cron 回刷 |
| is_pinned / pinned_at | 给动态流把视频当作品置顶 |
| tags | 多对多 `video_tags`，本表没有 tags 列 |
| is_original | 默认 true |
| storage_type | 有索引 |
| status | 默认 1，有索引 |

### `video_tags`（没有 struct）

复合主键 `video_id` + `tag_id`。没有时间列。`tags` 或 `video_tags` 一变，River 会重写对应视频的搜索文档，而不是把桥表本身索引进去。

### `tags`（含 Model）

name varchar(64)，有普通索引，**不是唯一**。同名标签在库里可以有多行，这是历史事实，面试时不要替它圆成唯一。

### `video_parts`（含 Model）

video_id（索引）、title varchar(200)、sort_order 默认 0（越小越前，有索引）、duration 秒、danmu_count、storage_type。一个作品多 P 时，转码消息带 `videoPartId`。

### `video_resources` 与 `video_part_resources`（都含 Model）

两张表列一样，只是外键不同：`video_id` 或 `video_part_id`。

| 列 | 要点 |
|---|---|
| resolution | varchar(64)。和上面的清晰度字符串，或 `自适应` |
| source_file_name | varchar(255) |
| file_url | varchar(500)。MP4 直链，或 `.../dash/manifest.mpd` |
| file_size | 字节 |
| bitrate | kbps。DASH 那一行是 0 |
| format | varchar(10)。实际写入 `mp4` 或 `dash`。注释里的 m3u8 没有被转码写入 |
| codec | varchar(20)。转码写入 `h264` |
| is_vip | 默认 false。高码率 1080 和 1600 以上的阶梯会标 true |
| is_souce_video | 拼写就是错的，外部契约。源片为 true |

唯一索引 `uk_video_resources_variant (video_id, resolution, is_souce_video)`，分 P 表是 `uk_video_part_resources_variant (video_part_id, resolution, is_souce_video)`。所以同一清晰度可以有一条「源」和一条「转码产物」。

### `video_likes`（含 Model）

video_id、user_id。唯一 `(video_id, user_id)`，另有 `(user_id, video_id)` 方便查「我赞过的」。

### `video_coins`（含 Model）

video_id、user_id、coins 默认 1，业务限制 1～2。唯一 `(video_id, user_id)`，同一人对同一视频只有一行，改的是枚数。

### `video_play_histories`（无单独 id）

复合主键 user_id + video_id。progress 秒、duration 秒、created_at。没有 updated_at 字段；再次观看会更新这行的进度（更新语义在仓储里，不是靠 GORM 的 UpdatedAt）。

### `favorite_folders`（含 Model）

user_id（索引）、name varchar(50)、is_default 默认 false。

### `favorite_folder_videos`

复合主键 favorite_folder_id + video_id，另有 created_at 且有索引。没有 updated_at。

### `video_reports`（含 Model）

reporter_username varchar(50)、video_id、reason varchar(200)、detail text、image_urls JSON、status 默认 1（1 待处理，2 已处理，3 已驳回）、handle_note varchar(500)、handled_by、handled_at 可空。

## 5. MySQL：评论、弹幕、动态、通知、轮播

### `comments`（含 Model）

content text NOT NULL、user_id、video_id 默认 0、dynamic_id 默认 0、comment_type（`video` / `dynamic` / `article`）、parent_id 可空、root_id 可空、at_user_ids JSON、pictures JSON、like_count、reply_count、is_pinned、pinned_at、commenter_ip varchar(20)、commenter_addr varchar(255)。

树的读法：根评论 `parent_id` 为空；回复指向父评论，并用 `root_id` 挂到楼层，避免递归查。专栏类型在枚举里，当前主路径是视频和动态。

### `comment_likes`（含 Model）

comment_id、user_id，联合唯一。热路径先写 Redis，30 秒刷回这张表。

### `danmu`（含 Model，表名单数）

user_id、video_id、video_part_id 默认 0、content text、time_offset 秒、color 默认 `#FFFFFF`、font_size 默认 25（tinyint）、position 默认 0（0 滚动，1 顶部，2 底部）、like_count。

索引：`(video_id, time_offset)` 和 `(video_id, video_part_id, time_offset)`。拉弹幕按时间轴，不按主键扫。

### `danmu_likes`（含 Model）

danmu_id、user_id，联合唯一。

### `danmu_reports`（含 Model）

和视频举报同形：reporter_username、video_id、danmu_id、reason、detail、status、handle_note、handled_by、handled_at。

### `dynamics`（含 Model）

user_id、content text、image_url varchar(500)、like_count、is_pinned、pinned_at。

### `dynamic_likes`（含 Model）

dynamic_id、user_id。两个联合索引方向相反：`(dynamic_id, user_id)` 唯一，以及 `(user_id, dynamic_id)`。

### `dynamic_reads`（含 Model）

唯一 `(user_id, author_id)`。一行表示「我读这个作者读到哪」：last_read_work_type、last_read_work_id、last_read_work_at（有索引）。未读数是拿这个水位和作者新作品比较，不是每条动态一行已读。

### `user_global_notifications`（含 Model）

| 列 | 含义 |
|---|---|
| type | 1 回复或在我的视频下评论，2 赞视频，3 赞评论，4 赞动态，5 @我，6 系统 |
| receiver_id | int，不是 uint。大于 0 是个人；**-1 是全员广播** |
| action_user_id / action_user_avatar / action_user_name | 操作者快照，避免之后改头像还要回表 |
| title / content / link | 文案和可选外链 |
| video_id / video_title / dynamic_id / comment_id | 跳转目标的快照 |

索引 `(receiver_id, type)`。

### `notification_user_reads`

复合主键 user_id + notification_id，另有 created_at。**有行才是已读**。全员广播不能给每个人预插一行，所以用这张稀疏表。未读 = 我该看的通知里没有已读行。

### `banners`（含 Model，无 TableName）

cover varchar(255)、href varchar(255)、show 默认 true、type 默认 1、partition_id 默认 0。

type：1 首页/分区轮播（partition_id=0 表示首页），2 顶部横幅，3 用户主页横幅。

## 6. Redis

客户端是 go-redis。Redis 挂了时，不少缓存会降级（搜索退 MySQL、弹幕退单进程），限流脚本失败则要看调用方：登录中间件失败会报「登录服务繁忙」（失败即拒绝），空 limit 的限流器本身是失败放行。

没有 JWT 黑名单。

### 6.1 限流（字符串计数，Lua `INCR` + `PEXPIRE`）

| Key | 限额 | 窗口 |
|---|---|---|
| `login:rate:ip:{ip}` | 30 | 10 分钟 |
| `login:rate:acct:{ip}:{username}` | 10 | 10 分钟 |
| `captcha:email:send:rate:email:{type}:{email}` | 5 | 10 分钟 |
| `captcha:email:send:rate:ip:{type}:{ip}` | 20 | 10 分钟 |
| `captcha:email:verify:rate:id:{emailID}` | 10 | 10 分钟 |
| `captcha:email:verify:rate:email:{email}` | 10 | 10 分钟 |
| `captcha:email:verify:rate:ip:{ip}` | 10 | 10 分钟 |

### 6.2 验证码和 OAuth

| Key | 类型 | TTL | 值 |
|---|---|---|---|
| `captcha:email:{emailID}` | string | 配置 `isExpire` 分钟，示例 10 | `{"code","email"}`，校验用 GETDEL |
| `captcha:click:{uuid}` | string | 配置秒数，否则 2 分钟，示例 300 秒 | 点选坐标，GETDEL |
| `captcha:slide:{uuid}` | string | 同上 | 滑块答案，GETDEL |
| `oauth:state:{provider}:{state}` | string | 10 分钟 | `"1"`。Redis 没有时退到进程内 map |

OAuth 五家：GitHub、Google、QQ、X、LinuxDo。state 用来挡 CSRF。

### 6.3 用户状态

| Key | TTL | 作用 |
|---|---|---|
| `user:status:{id}` | 60 秒 | 状态整数 |
| `user:status:gen:{id}` | 2 分钟 | 代数。写入前记下代数，Lua 只有代数没变才回填，避免旧的「正常」覆盖刚写入的封禁 |

### 6.4 视频详情和计数

| Key | 类型 | TTL | 作用 |
|---|---|---|---|
| `video:detail:meta:{id}` | string | 5 分钟 | 标题、作者、资源、分 P 等 JSON |
| `video:detail:meta:gen:{id}` | string | 10 分钟 | 和用户状态一样的代数锁 |
| `video:detail:stats:{id}` | string | 7 天，每次变更刷新 | views、likes、commentCount、coinCount、favoriteCount、danmuCount |
| `video:detail:stats:ver:{id}` | string | 7 天 | 每次成功增量 +1 |
| `video:detail:stats:dirty` | set | 无 | 成员是视频 ID。Cron 刷库成功后，只有版本仍等于快照才 SREM |
| `video:author:id:{videoID}` | string | 30 天 | 作者用户 ID。作者变更必须删 |

计数是权威热数据，不是「缓存了 MySQL」。`Seed` 用 SETNX，不覆盖已经更热的值。减收藏时如果 key 不存在就不动，避免用旧的库值再减一次。

**一次计数写入如何走：** 未命中时先读 MySQL 作为基线；Lua 在一个 Redis 原子操作里更新六个字段、`SADD dirty`、递增 `ver`。读路径优先 Redis，未命中再回 MySQL 并用 SETNX 回填。回写任务原子读取「计数 + 版本」快照，成功写 MySQL 后，只有版本没变才移除 dirty；若期间又有增量，下一轮仍会回写。这里的版本保护的是「不要漏掉回写期间的新写入」，**不是**跨 Redis 和 MySQL 的事务。

故障处理要分清：没有配置 Redis 时直写 MySQL；Redis 已配置但一次 Lua 写失败时，普通增量重试后保留原缓存并返回错误，避免执行结果不明却又在 DB 加一次；投币/三连等账本已提交的路径使用 `ApplyCommittedDelta`，失败后尝试 DB 增量并清理 Redis。DB 回写滞后期间 Redis key 过期或丢失会带来数据恢复风险，因此这套实现不能声称计数零丢失。可通过持久化设置、对账和可靠事件日志继续加强。

### 6.5 定时发布、热榜、热搜

| `video:hot:zset` | zset | 热度 | 互动加分。每 10 分钟乘 0.97，低于 0.01 删掉，超过 200 条丢掉最低的 |

## 7. Kafka

只用 IBM sarama，业务上只有一条转码流。

| 配置项 | 示例 |
|---|---|
| 逻辑名 | `transcode` |
| 物理 topic | `video_transcode_tasks` |
| 死信 | `video_transcode_tasks.dlq` |
| 消费组 | `f-ccg-video-transcode-group` |
| clientID | `f-ccg-video-server` |
| 版本 | 3.9.0 |

生产者：同步发送，`RequiredAcks=WaitForAll`，重试 5 次。消息只有 topic 和 body，没有 key，没有 header。`kafka.enable=false` 时发布直接失败。

消息体（json tag 是契约）：

| JSON | 含义 |
|---|---|
| resolution | 高度数组，例如 360、720、1080 |
| storageType | 存储类型 |
| sourcePath | 源对象路径 |
| outputPath | 产物前缀 |
| fileHash / fileName | 文件身份 |
| videoId | 作品 ID |
| videoPartId | 分 P，单 P 作品可省略 |

死信 body 另含 topic、partition、offset、原始 value、error、failedAt。

消费者：

- 再均衡策略 Range。会话超时 45 秒，心跳 10 秒。再均衡等待默认 **4 小时**，因为一条转码可能很长。
- 组里没有位点时从最早的消息开始。
- 自动提交开着，但只有 `MarkMessage` 之后才会提交。
- 一个分区同时只处理一条。worker 池默认 2，示例 yaml 是 4，限制的是同时跑的 ffmpeg。
- 进程内再试 3 次（一共 4 次），间隔 500ms、1s、1.5s。仍失败则不标记，交给 Kafka 重投。检查点让重投从上次完成的段继续。
- 坏 JSON、缺字段、没有转码配置：写死信再标记。死信写失败则不标记。
- 视频已硬删：清进度、标记位点、不重试。
- 启动连不上会退避重试，2 秒起，封顶 30 秒，15 分钟后放弃。放弃也不让 HTTP 起不来。
- `Errors()` 通道没有人读，这是代码注释里承认的缺口。

**交付语义要说准：** 处理成功才 `MarkMessage`，Sarama 后续自动提交已标记位点，因此消费是**至少一次**，不是恰好一次。成功处理后、位点实际提交前如果重启，同一消息仍会重投；转码检查点和资源变体唯一索引帮助恢复与去重，但跨对象存储、DB、Kafka 不存在原子事务。非永久错误在进程内重试耗尽后返回且不标记，等待重新消费；**不会因为重试次数耗尽就自动进 DLQ**。只有解码/字段/配置等被归类为永久错误的消息，在死信发送成功后才标记原消息。排查卡住的分区要同时看消费者日志、进度 key、源 topic 位点和 DLQ。

## 8. MongoDB

只给私信。库名是配置里的 `mongo.db`。没配或库名为空时客户端是 nil，私信不可用，别的接口还在。`RetryWrites=true`。启动时建索引，10 秒超时，失败只警告。

### 集合 `chat_messages`

| 字段 | 含义 |
|---|---|
| _id | ObjectID，插入前由应用生成 |
| conversationId | `较小用户ID_较大用户ID` |
| senderId / receiverId | 用户 ID |
| type | text / image / emoji / sticker |
| text / emoji | 可省略 |
| media | url、mime、width、height、size |
| createdAt | 时间 |

索引：

1. `conversationId_id_desc`：`{conversationId:1, _id:-1}`，翻页
2. `conversationId_sender_receiver_createdAt_desc`
3. `receiverId_id_desc`

### 集合 `chat_conversations`

`_id` 就是会话键，不是 ObjectID。

| 字段 | 含义 |
|---|---|
| participants | `[较小ID, 较大ID]` |
| memberA / memberB | userId、unread、visible、lastReadAt、lastReadMsgId。最后一个字段在 PO 中定义，但当前 `MarkRead` 只更新 `lastReadAt` 和未读数，不写它 |
| lastMessage | msgId、type、preview、senderId、createdAt |
| createdAt / updatedAt | |

发送：先插入消息，再按 `_id` upsert。`$setOnInsert` 写参与者和发送方未读 0；`$set` 写最后一条、两边都可见；`$inc` 接收方未读。

索引：`participants_updatedAt_desc`。

在线推送不走 Mongo change stream，走 Redis `chat:user:{id}`。

**原子性边界：** `$set` 最后一条与 `$inc` 未读发生在同一个会话文档更新中，这是 Mongo 单文档原子性；`chat_messages.InsertOne` 与 `chat_conversations.UpdateByID` 是先后两次操作，没有 Mongo 事务。若消息插入成功而会话更新失败，接口报错但历史消息可能已经存在，会话列表/未读可能没推进；重试也没有客户端幂等消息 ID 去保证只插一条。当前不能宣称端到端恰好一次或两集合强一致。工程上可引入客户端消息幂等键、唯一索引和补偿/对账，再视需要使用 Mongo 事务。Pub/Sub 消息本身不持久化，断线后应从 Mongo 补拉。

## 9. Elasticsearch 与 River

两套客户端：关键词和 River 用 olivere v7；向量用官方 v8。嗅探和健康检查关掉。ES 没配时关键词搜索退回 MySQL。

### 9.1 `search_videos`

3 分片 1 副本。分析器 `ik_pinyin` = IK 最细切词 + 小写 + 拼音（首字母、全拼、保留原文）。`dynamic: true`。由 CLI `-es` 按 `videos_mapping.json` **删掉再建**，HTTP 启动不会自动建。

| 字段 | 映射 |
|---|---|
| id | long |
| title | text，索引 ik_max_word，搜索 ik_smart；子字段 keyword、pinyin |
| cover | keyword |
| author_username | text ik_smart；keyword、pinyin |
| tags | text；keyword、pinyin |
| title_suggest / tag_suggest | completion。当前查询路径已经不用 completion API，字段仍由 River 写入，未发布时写成 null |
| views / danmu_count | long |
| duration | integer |
| created_at | date |
| status | integer |

文档 `_id` 是 `videos:{id}`。查询是 bool should，至少命中一条，并且 `status=已发布`。title 权重 5，title.pinyin 3，tags 4，tags.pinyin 3，keyword 前缀也有权重。排序可以按播放、弹幕、时长，默认按相关度。高亮 title 和 tags。

### 9.2 `search_users`

2 分片 1 副本。`_id` 是 `users:{id}`。

| 字段 | 映射 |
|---|---|
| id | long |
| username | text ik_smart；keyword 带小写 normalizer；pinyin |
| username_suggest | completion，查询路径同样不走 completion API |
| description | text；只有 pinyin 子字段 |
| avatar | keyword |
| level | integer |
| follower_count | long |
| follow_usernames / friend_usernames | text + keyword + pinyin。friend 是互关 |
| created_at / updated_at | date |

用户查询没有 status 过滤。精确用户名权重最高。@ 提及会先用候选 ID 做 terms 过滤再套用户名查询。

### 9.3 `search_videos_vector`

名字来自 `ai.vectorIndex`，示例就是这个。1 分片 0 副本。River 和 `-es` 都不创建它。

| 字段 | 类型 |
|---|---|
| video_id | long |
| title / tags / partition | text + keyword |
| description / content | text。content 是「标题、描述、分区、标签、分 P」拼出来的合同文本 |
| cover | keyword，不索引 |
| status | integer |
| created_at | date |
| has_image_vector | boolean |
| content_vector | dense_vector，1024 或 2048 维，默认 2048，余弦，可索引 |

`_id` 同样是 `videos:{id}`。改维度必须删索引重建，ES 不能原地改 dense_vector 的维数。未发布的视频从这套索引删除，而不是更新。

检索：kNN 的 k 等于 limit，num_candidates 至少是 limit 的 20 倍且不少于 100，过滤已发布。有文本时再做一条 multi_match（title^3、tags^2、partition^2），和向量结果按 RRF 融合，排名常数默认 60。ES 的余弦分数是 `(1+cosine)/2`，所以配置里的最低相似度要先换成这个尺度。只有图片的查询不做关键词融合。

封面参与向量由 `embeddingImageMode` 决定：on 必须有封面，off 只用文字，其他值（含空）是 auto。相对路径用 `assetBaseURL` 补成绝对地址；本地封面会抓下来变成 data URI。

重建接口：`POST /v1/admin/video/vector/rebuild`，状态 `GET /v1/admin/video/vector/status`。进程内单飞，每页 200，默认 4 个 worker，上限 16，超时 6 小时。

### 9.4 River 怎么同步

canal 订 binlog，要求 `binlog_row_image=FULL`。位点是文件加偏移，存在 `{dataDir}/master.info`，示例 `./runtime/river`。先把 ES bulk 写出去，再记位点。批量 128 或 200 毫秒，单次超时 3 秒，可重试错误最多 5 次。写失败就取消同步，位点不往前走，避免「位点过了、文档没了」。

示例 `config_dev.yaml` 订阅五张表：`videos`、`users`、`tags`、`video_tags`、`user_focus`。真正的 ES 规则只有两条：videos → `search_videos`，users → `search_users`。

| 表上的事件 | 动作 |
|---|---|
| videos 插入 / 更新 / 删除 | 按规则写或删 `videos:{id}`。发布状态才写 suggest 字段 |
| users | 写 `users:{id}`，并补粉丝数、关注用户名、互关用户名。只改 `updated_at`（硬币、经验）不算相关变更，不重建 |
| video_tags | 找出 video_id，从 MySQL 重装视频文档 |
| tags | 找出用了这个标签的视频，重装 |
| user_focus | 示例配置没有这条 rule。只订了 source、没有 rule 时，行事件会被忽略。粉丝数会在用户文档因为别的原因重建时补上 |

`config.example.yaml` 里 River 是关的，rules 是空的。面试时说「开发配置开着，示例配置默认关」。

**索引一致性边界：** River 是 MySQL 提交后的异步投影；ES Bulk 成功后再保存 binlog 位点，故位点未保存就重启可能重放同一事件，固定 `_id` 的覆盖写入使重放可接受。Bulk 失败会停止同步而不推进位点，避免静默跳过；这不等于零延迟或跨 MySQL/ES 的强事务。`search_videos_vector` 不由 River 维护，走应用的异步向量同步/手动重建，故关键词索引与向量索引也可能暂时不一致。排障先确认 River 是否启用、source 是否订表、rule 是否匹配、位点和 ES Bulk 错误，再看向量同步状态。

server id 示例是 3012，代码默认 1001。同一 MySQL 上不能和别的 canal 撞 server id。

| POST | `/v1/admin/rbac/menu/generate` | 管理权限 | 用聊天模型填菜单字段 |

聊天没有服务端会话。前端每次提交完整 `input`。历史默认留 20 条、24000 个字符，系统消息保留，窗口从前面裁到以 user 开头。正式回答 4096 token；找视频前的意图分析 256 token。思考关闭时强制关；开启且没传强度时用 `high`。DeepSeek 把 low/medium 折成 high，把 xhigh 折成 max。

找视频：分析出最多 6 个关键词 → 方舟向量 kNN，和关键词 RRF → 失败则 SQL LIKE 已发布视频 → 再没有就取最新。默认候选 8 条，提示词要求模型最多回 5 个链接，并且原样抄 `/video/{id}`。聊天图片不会作为视觉块发给聊天模型，只变成文本标记；最多 3 个 URL，只有第一张去嵌入。

生视频是任务不是文件。Seedance 1.5 pro 时长 4～15 秒，1.0 pro fast 是 2～12 秒，其他模型 ID 放行 1～15 秒。分辨率只认 480p/720p/1080p，非法值丢掉而不是报错。

没有按用户的 AI 配额，也没有扣硬币。成本控制是模型白名单、90 秒的路由超时、历史裁剪、图片张数上限。上游报错如果文本里有 API Key、未配置、不支持，会原样给前端，否则统一成「AI 服务暂时不可用」。

代码不调用 xAI。模型名里带 grok 会被换成配置的默认聊天模型。

## 13. 面试时怎样讲，以及可能被追问什么

### 60 秒版本

> 用户、视频、关系和权限以 MySQL 为准；私信消息与会话在 Mongo。Redis 除普通缓存外，还承载视频热计数、评论点赞待回写意图和实时 Pub/Sub；定时计划保存在 MySQL 视频行。Kafka 只承载耗时转码，消费成功标记位点，重投靠检查点和资源唯一索引收敛，永久错误送 DLQ。搜索有两条独立读模型：River 订 MySQL binlog 维护关键词索引，应用异步维护向量索引。它们都允许短暂延迟，所以我会先指出每条链路的权威数据和失败恢复方式。

### 追问 1：为什么视频统计不直接每次写 MySQL？怎么证明不会把新计数覆盖掉？

高频观看/互动若每次更新同一视频行，会使热点行成为写入瓶颈。现有实现用 Redis Lua 原子加增量，并把视频 ID 放入 dirty set；5 分钟回写时同取计数和版本。落库后仅在版本未变化时摘除 dirty，期间新增量就留到下一轮。必须补一句：这是避免**漏刷并发增量**，不是 Redis 与 MySQL 的强一致；Redis 丢数据、TTL 过期和 DB 回写失败仍需要持久化和对账策略。定位：`internal/infrastructure/cache/video/stats_cache.go`、`internal/infrastructure/scheduler/video_stats_cache.go`、`internal/application/platform/video_stat_sync_service.go`。

### 追问 2：Kafka 重试四次就一定进死信吗？会重复转码吗？

不会。代码区分永久错误与可重试错误：坏 JSON 等永久错误成功写 DLQ 后标记位点；可重试错误在本次进程内最多四次尝试，仍失败就不标记，后续可能重投。标记与 Kafka 自动提交也有时间窗，因此重复消费是正常边界。处理需要能承受重复执行，当前有本地检查点和资源变体唯一索引；对象存储写入与 DB 写入并非一个原子事务。定位：`internal/infrastructure/mq/kafka_consumer.go`、`internal/infrastructure/mq/transcode_consumer.go`。

### 追问 3：Mongo 会话里未读数原子更新，是否就保证私信完全不丢不重？

只能保证一次会话文档更新内的未读与最后一条一起生效。发送先插 `chat_messages`，再更新 `chat_conversations`，两次写之间可能失败；没有消息幂等键或跨集合事务。Redis Pub/Sub 只是在线提示，消费者离线后从 Mongo 补拉。定位：`internal/application/chat/chat_service.go`、`internal/infrastructure/persistence/chat/store.go`。

### 追问 4：改标签、关注人数以后，ES 会马上准确吗？

标签及桥表事件会按受影响 ID 从 MySQL 回源重建视频文档；普通视频/用户行则按规则写索引。`user_focus` 有特殊重建逻辑，但仍需配置对应 rule；当前 `config_dev.yaml` 只订阅它，没有该 rule，故单独关注变更不会立即更新 ES 用户文档。River 的 binlog 投影是最终一致，向量索引又是另一条异步链路。定位：`internal/infrastructure/river/sync.go`、`config_dev.yaml`。

### 追问 5：当前角色切换后，权限是否只按新角色计算？

不能这样说。`SwitchRole` 验证用户拥有目标角色并更新 `users.current_role_id`；中间件实际以 `user:<id>`、请求路径和方法问 Casbin，`g` 中的用户角色绑定决定可用策略。当前角色还影响菜单选择，但切换方法没有重新绑定 Casbin 角色。`api_resources` 用于管理界面列接口，`role_menus` 用于菜单，不直接等于后端鉴权。定位：`internal/application/identity/account_service.go`、`internal/interfaces/http/middlewares/casbin_auth.go`、`conf/rbac_model.conf`。

### 追问 6：定时发布服务多实例部署时会重复发吗？

多个实例可能从 MySQL 扫描到同一个候选 ID，扫描本身不领取任务。每个实例进入行锁事务后重新检查视频状态与 `publish_at`；只有实际更新为已发布者触发后续向量同步，后来的实例见到已发布即跳过并保留计划历史。扫描后改期也会在锁内重检时被识别，失败返回供后续轮询重试。调度不依赖 Redis。定位：`internal/application/video/scheduler.go`、`internal/infrastructure/persistence/video/schedule_store.go`。
