# 面试问答

这份是**口头回答练习稿**，以当前工作树代码为准。先读每题第一段，能在 30～60 秒内讲清主线；面试官继续追问时，再补机制、失败语义和边界。只有亲自做过的工作才能说成个人贡献，其余用“项目里这样实现”。如果还没学过 DDD，先读[从零读懂本项目的 DDD 架构](../DDD-从零到读懂本项目.md)；媒体原理见 [02-架构与媒体原理.md](./02-架构与媒体原理.md)，数据细节见 [03-基础设施与数据设计.md](./03-基础设施与数据设计.md)，完整代码分层见 [../architecture.md](../architecture.md)。

每段回答都按这个顺序，避免从配置值背起、讲了两分钟还没有结论：

1. 先给结论。
2. 按时间讲一条链路，点出权威数据在哪里。
3. 讲一个真正会发生的失败及恢复办法。
4. 最后说当前边界和你会如何验证或改进。

**先把四个词讲准**：MySQL 事务成功是“稿件已保存”；Kafka 投递成功是“转码任务已入队”；资源行和对象均存在才是“该档可播”；审核、定时、私密决定“公众是否可见”。这四个状态没有合并为一次原子操作。详见 `internal/application/video/publish_service.go`、`internal/infrastructure/mq/transcode_consumer.go`。

## 1. 开场（这段背下来）

**面试官：介绍一下你这个项目。**

这是一个按业务上下文组织的 Go 视频站后端，默认同进程运行，也支持独立转码消费者。用户能投稿、看多清晰度、发弹幕和评论、关注、发动态、私信。管理端做审核、封禁和权限。

我习惯把它拆成两条时间尺度。短的是 HTTP：登录签发 JWT，管理接口再过 Casbin，稿件、点赞关系、硬币账本和评论正文等权威数据写 MySQL。播放量等展示计数走 Redis 热路径，脏数据定期回刷 MySQL；不能把“关系已写库”和“展示数字已回刷”说成同一件事。

默认后台组件由同一个服务进程启动，转码消费者可改用独立入口运行。投稿先提交 MySQL，再由进程内异步任务向 Kafka 的 `video_transcode_tasks` 投递；HTTP 响应不等待投递成功，后台任务与响应的实际先后由运行时调度决定。消费者用 FFmpeg 产出多档 MP4 和 DASH，清单是 `manifest.mpd`。MySQL binlog 经 River 更新 Elasticsearch 关键词索引；向量索引另走应用侧写入。私信消息、会话和未读存在 MongoDB，在线推送经 Redis Pub/Sub。

所以线上出问题，我先确认是权威写入失败、异步投递失败，还是转码、索引同步、计数回刷的滞后。每条链路都有不同的重试和补偿边界。

**他接着问：你个人做了哪一段？**

挑你真正负责的一段，按“需求、方案、最难的失败场景、验证结果”说。比如上传链路可以讲“先按用户和哈希占当天额度，再用跨实例哈希锁协调上传、发布和清理；发布时在锁内复核源对象并落库”。如果你只修了其中一环，就准确说那一环。转码链路则要主动说明：投稿成功不等于 Kafka 投递成功，因为投递在异步回调中，当前没有持久化 outbox。

**他接着问：为什么不拆成微服务？**

默认 `cmd/server` 把 HTTP、River、定时任务和转码消费者装配在同一进程；现在也可通过 `cmd/transcode-consumer` 单独运行消费者，并在 HTTP 节点设置 `transcode.localConsumerDisabled: true` 后重启，保留投稿投递但跳过本机消费。独立入口不受这个开关影响，不启动 HTTP、River 或 Cron。同消费组按 topic 分区分摊任务，跨机器还要保证 MySQL、Redis、Kafka 和源文件存储可达。单独部署转码节点可以隔离机器资源和调整容量，但没有补上投稿到 Kafka 的可靠投递缺口，也不等于所有上下文都已拆成微服务。HTTP App 的后台组件启动失败只记日志并继续，独立消费者启动失败返回非零退出码。证据见 `internal/bootstrap/runtime.go`、`internal/bootstrap/transcode_worker.go` 和[独立消费者说明](../../cmd/transcode-consumer/README.md)。

画完补三句，这三句是他接下来的题：

私信只有 Mongo 两个集合，别的业务不进 Mongo。关键词搜索走 binlog，向量索引不走 binlog，是发布时用方舟嵌入写进去的。播放文件是 MP4 直链加一个 mpd，没有 m3u8。

打开[交互架构图](./diagrams/system-architecture.html)练习四个引导视图：投稿、转码、关键词搜索、缓存与私信。MongoDB 已画在图上；AI 适配器收在说明卡里，OAuth 可按追问补充。

**他接着问：启动顺序为什么是这样？**

先起会消费数据的后台，再接流量。顺序是 River、定时发布调度器、转码消费者、Cron、聊天 Hub、弹幕 Hub。某一个失败不让整个进程退出。停止时反过来：先把 HTTP 停掉，不再产生新的转码和搜索写入，然后停转码、调度器、River、Cron 和两个 Hub，最后关 Mongo、MySQL、Redis、ES。先停入口，再停写数据的人，最后关连接。

## 3. 登录、权限、封禁

**面试官：用户登录之后，下一次请求你怎么知道他是谁？**

无状态 JWT，HS256。access 里是 uid、username 和过期时间，refresh 里是 uid 和过期时间，两把密钥分开。配置里的过期单位是天，签发时乘 24 小时。服务端不存 token，也没有黑名单。退出登录只是浏览器把 token 丢掉。过期之前被拿走的 access 仍然能用，这是这套方案的边界。封禁不靠作废 token，靠下面那道状态检查。

**他接着问：封禁后旧 token 为什么还可能有效？**

JWT 本身不吊销。封禁把 `users.status` 和 `user_ban_records` 放进同一个 MySQL 事务；提交后将新状态写穿 `user:status:{id}`（TTL 60 秒），并递增 `user:status:gen:{id}`，旧请求读到的 Active 不能再覆盖新状态。Redis 正常时，新请求应很快看到新状态；Redis 写失败时不能承诺“立刻”，读路径未命中会回源 MySQL。**校验范围也要说准**：`JwtAuth` 对永久封禁做拦截，普通临时封禁主要靠投稿、评论、弹幕等写操作上的 `UserBanCheck`，不能宣称所有接口一律禁用。临时封禁到期既有每 5 分钟的 Cron，也有内容操作上的到期解封检查。证据见 `internal/application/identity/ban_service.go`、`internal/application/identity/user_status_service.go` 与两个中间件。

**他接着问：管理接口和普通登录有什么不同？**

登录只证明你是这个 uid。管理接口还要过 Casbin。模型是主体、路径、方法。有一条 allow 就通过。匹配器是 glob，策略可以写 `/v1/admin/**`，方法可以是具体动词，也可以是 `*`。`casbin_rule` 里 `p` 行是接口策略，`g` 行是用户和角色。菜单表只负责前端画侧边栏，不负责放行。`-rs` 把 Gin 上的真实路由同步进 `api_resources`，后台按这张清单勾权限，避免手写路径和代码漂移。

**他接着问：第三方登录怎么防伪造回调？**

跳转前写 `oauth:state:{平台}:{state}`，十分钟，回调里 GETDEL。用过就没了，重放无效。Redis 没有的时候退到本进程的 map，多实例时这条退路只在拿到 state 的那台机器上有效。五家是 GitHub、Google、QQ、X、LinuxDo。邮箱用户没有 open_id，库里存 NULL，再加 `(open_id, register_source)` 唯一索引。MySQL 的唯一索引允许多个 NULL，所以多个邮箱用户不会互相撞。这里不用函数索引，因为 River 用的 canal 解析不了那种 DDL，binlog 同步会直接断。

**他接着问：改硬币为什么曾经把第三方绑定清掉？**

User 在保存前要把空白 open_id 写成 NULL。早一版对所有更新都 SetColumn。GORM 用 map 做部分更新时，这个调用会把 open_id 塞进本次要写的字段。于是一次只改 `coin_count` 的语句变成同时 `open_id = NULL`。现在只有这次更新真的带了 open_id，才做这个规范化。

## 4. 投稿到能播（他会让你从头讲）

**面试官：用户上传一个 2GB 的视频，到能播放，中间发生什么？**

按“上传对象、保存稿件、异步生成资源”三段讲，别把它们说成同一个事务。

第一段是上传。客户端按文件哈希和从 0 开始的序号传分片。服务端先检验投稿开关、登录与封禁，再按用户和哈希占当天额度；普通用户默认每天最多 10 个不同源文件，管理员豁免，同一哈希当天重试不重复计数。分片、完成对象、投稿和清理用 Redis 哈希锁协调。完成时校验分片连续，再由本地或 MinIO 驱动合并；结果是 `_source_<哈希>.mp4`。状态接口只在重新确认完整对象存在后才返回秒传，不能仅相信进程内的已完成缓存。额度按“尝试过的不同文件”计，失败和放弃不退。

第二段是投稿。在同一组哈希锁内重验源对象、占额度并提交视频、标签、分 P 与初始资源的 MySQL 事务；审核和定时规则决定初始状态。MySQL 事务成功后启动进程内异步任务，写定时 ZSET、同步向量、向 Kafka 投递转码消息；接口不等待这些动作完成，投递成功后把 Redis 进度标为 queued。逻辑 topic 叫 `transcode`，示例物理 topic 是 `video_transcode_tasks`。消息带源路径、哈希、视频/分 P ID、分辨率及输出路径。这是当前最需要主动交代的一致性边界：异步任务或投递失败时，视频行可能已提交，但并没有可靠的转码任务记录。

第三段才是转码。源资源在投稿事务内已经作为初始资源保存；消费者再 probe 媒体元信息，并按开关生成 MP4 和 DASH。成片先落转码机本地，校验后上传对象，再保存新的资源行并失效详情元数据缓存，前端随后才能看到新增清晰度。**能看到稿件与源资源，不代表转码任务已入队或成片已可用。**

**他接着问：为什么不在发布接口里转完再返回？**

一部片子可能转几十分钟，直接在 HTTP 请求内做会耗尽请求窗口和工作机资源。消费者通过 Kafka 异步处理，并用对象、资源行和本地检查点处理重投。不过“异步”只解决耗时问题，不能自动保证 MySQL 与 Kafka 原子提交；当前投稿后投递由进程内任务承担，进程在两者之间退出就可能漏投。我会用事务 outbox、可重扫的待投递记录或定期对账补偿来收敛这个窗口。源资源在投稿事务内保存，但能否播放仍要看源对象是否可访问，以及当前审核/私密状态是否允许查看。

**他接着问：消息没有 key，分区怎么定？**

消息没有显式 key，分区由生产者默认策略决定，同一视频的多条消息没有固定分区顺序保证。消费者以目标 URL 已入库且对象大小大于 0、以及本地已校验的检查点作为重投复用依据。这能减少重复编码，但不等于跨 MySQL、Kafka、对象存储的端到端 exactly once；对象上传和数据库写入之间仍可能留下孤儿对象，需要清理或对账。

**他接着问：消费失败会丢消息吗？**

Kafka 生产者配置 `WaitForAll` 和最多 5 次重试，但这只约束**已经执行的投递**。消费者处理成功会 MarkMessage；坏消息等永久错误先发死信，死信写成功也会标记。普通失败进程内最多处理 4 次，间隔半秒、一秒、一秒半；仍失败则结束当前 partition claim，不标记该位点，等待后续消费会话重投，不能说它马上自动重试成功。视频硬删属于可结束任务，清进度并标记。再均衡窗口配置较长，避免长任务过早移交，但停机、再均衡仍可能重投，所以处理过程必须允许重复执行。

## 5. 转码本身（区别度最高的一段）

**面试官：MP4 和 DASH 你都有，页面上到底播哪个？**

详情接口把资源按清晰度排序，`自适应` 排第一。这一行的 format 是 `dash`，file_url 指向 `manifest.mpd`。其他行 format 是 `mp4`，是某一档的直链。前端看 format：dash 交给 dash.js，mp4 交给原生 video。原生 video 自己发 HTTP Range，对象存储回 206。我们没有再写一个 Range 服务器。

**他接着问：m3u8 是什么，你们为什么不用？**

m3u8 是 HLS 的播放列表，文本的。主列表列出每一档，每一档自己又是一个列表，里面是一串几秒一片的 ts 或 fMP4。播放器播完一片再决定下一片从哪一档拿。

我们走的是 DASH。FFmpeg 原生输出 `manifest.mpd`、每个 Representation 的初始化文件 `<hash>-init-stream<编号>.mp4` 和 `<hash>-stream<编号>-<五位序号>.m4s` 媒体分片；直接编码和分块 copy 封装都启用 `-use_template 1 -use_timeline 1`。分片目标时长默认 4 秒，实际时长读 MPD 的 SegmentTimeline，不能把每一段都当作精确 4 秒。每个视频流分别强制关键帧，NVENC 另加 `-forced-idr:v:<编号> 1` 保证 IDR 边界。校验器只读检查时间轴、引用文件和时长，不改写清单。先上传媒体文件，最后上传清单；清单和所有相对引用的初始化文件、分片都可访问才具备播放条件。

库字段的注释里写过 m3u8。**新转码产物**的 format 是 `mp4` 和 `dash`；投稿时保存的源资源 format 由源文件决定，可能是 `matroska` 等，不能把所有资源行都说成这两种。

**他接着问：faststart 解决什么？**

MP4 里除了画面，还有一个叫 moov 的索引，记录每一帧在哪个字节。它如果在文件尾，播放器必须先读到尾才能开播。`+faststart` 在编码结束后把 moov 挪到文件头。分段编码的中间块不加，最后用 `-c copy` 拼起来时再加。以前有过往 TCP 管道写的分支，那种输出不能回头改文件头，用的是另一组 movflags。现在的正式路径是先落成文件再上传。

**他接着问：CRF 是不是码率？**

不是。码率是每秒多少比特，库里的单位是 kbps。CRF 是质量旋钮，数字越小越清晰、文件越大。CPU 用 libx264 的 `-crf`，GPU 用 h264_nvenc 的 `-cq`。外面再加 `-maxrate`，bufsize 是它的两倍。平时按质量走，峰值不许超过这条线。如果源自己已经低于这一档的保底，上限就停在源码率，不会为了「达标」把文件越压越大。

**他接着问：720 和 1080 怎么决定压不压？**

配置里有 360、720、1080、2160，但不会比源的真实高度更高。滤镜是 `scale=-2:高度`，高度按阶梯，宽度按比例取偶数。源自己那一档用 null 滤镜，不放大。高码率指分辨率已经是 1080 高清或 4K，并且码率超过阈值。没配阈值时代码按 10000 kbps，示例配置是 8000。720p 的源不会被当成高码率。高码率会多一档「1080p 高码率」，标成会员资源。

**他接着问：两条管线有一条失败了，任务算成功吗？**

MP4 失败，整单失败，Kafka 位点不提交。DASH 失败时，如果这次本来就要出 MP4，整单仍可以成功，日志里是警告。只有 DASH、没有 MP4 目标时，DASH 失败才整单失败。已经传上去的 DASH 不会因为后面 MP4 失败而回滚。时长和源相差超过 2% 且超过 3 秒的成片作废，这一档不算成功。

**他接着问：GPU 挂了呢？**

先走 h264_nvenc。任务没被取消的话，失败就改 libx264。错误文本像是 CUDA、NVENC、没有设备，这个进程接下来 10 分钟不再尝试 GPU；驱动版本不匹配则是 6 小时。GPU 分段和 CPU 分段分开放，参数不同，不能拼进同一个成片。直接出 DASH 时，缩放仍在 CPU 上做，因为 dash 的封装要 CPU 侧的帧。回退的时候代码不再看 CpuMode 这个开关。配置只禁止 GPU 和 CPU 两个都关。

**他接着问：怎么发现 ffmpeg 卡死，而不是还在慢慢转？**

两套钟一起跑。墙钟大约是片长的 6 倍（GPU）或 20 倍（CPU），夹在 15 分钟到 12 小时。停滞看门狗看的是进度回调：允许停住的时间是片长秒数除以 3，再夹到 20 分钟到 90 分钟。进度来自 ffmpeg 的 `-progress`，解析 out_time。任何一次进度都算没卡。上传另按大约 512KB/s 估一个截止时间，那是超时，不是限速。

**他接着问：重启之后要从头转吗？**

不头转。库里这一档的 URL 已经是目标路径，并且对象大小大于 0，编码、上传、插入都跳过。检查点里有校验过的成片，就只上传。长视频默认 180 秒一段，缺哪段补哪段。最后一段不限制长度，避免探测时把小数秒截掉后丢掉尾巴。音轨不放进视频段里，整条单独编成 AAC，再拷贝混进去，免得段边界爆音。检查点以 rename 成功为准，写了一半的目录不会被当成完成。成功、视频被删、永久失败会删检查点。可重试的失败留着。超过 7 天没动的，每 12 小时清一次。

**他接着问：以前为什么会出现 CPU 掉到 0、进度永远不动？**

旧实现让 ffmpeg 多路输出写到本地 TCP，Go 边收边分片上传。多路输出要求每一路都被及时读走。任一路上传卡住，TCP 窗口满，整棵滤镜停住，没有成片，进度也不走。现在编码和上传分开：ffmpeg 写完本地文件并退出，再串行上传。

**他接着问：删视频的时候转码还在跑怎么办？**

本进程取消对应的 ffmpeg。同时往 `transcode:cancel:events` 发视频 ID，别的机器上的消费者也会取消。这种取消会提交 Kafka 位点、清掉 Redis 进度、删检查点，并尽量删掉已经传上去的 MP4 或 dash 前缀。进程退出或再均衡造成的取消不提交位点，检查点留着，下次接着做。

## 6. 计数、缓存、榜

**面试官：播放量是怎么加的？为什么不每次 UPDATE？**

详情上的播放、点赞、投币、收藏、评论、弹幕数，热路径在 `video:detail:stats:{视频ID}`，JSON，TTL 7 天，每次变更刷新。同时版本号加一，视频 ID 放进 dirty 集合。Cron 每 5 分钟把脏集合扫出来，用 Lua 一次读出计数和版本，写入 `videos`，只有版本还等于刚才的快照才从脏集合拿掉。版本变了说明刷库期间又有新增量，留给下一轮。

这样详情不用每次给 `videos` 行加行锁。正常情况下 MySQL 数字约落后一个 5 分钟回刷周期；Cron 或 Redis 故障时可能更久，Redis 在回刷前丢失则未落库增量可能丢。种子用 SETNX，不用旧库值覆盖更热的计数。减收藏时如果 key 不存在就不动，避免用过期库值再减一次。

**他接着问：详情缓存和这个计数会不会打架？**

会故意拆开。`video:detail:meta:{id}` 是标题、作者、资源列表，5 分钟，旁边有代数。转码落一档新资源就删掉它并抬高代数，进行中的旧读不能再把空资源写回去。计数不放在这块 meta 里，所以清详情不会把播放量清掉。

**他接着问：评论点赞为什么又做了一套队列？**

视频点赞是请求里直接写 `video_likes` 的唯一行。评论点赞更碎：Lua 看 set 里有没有这个用户，决定赞或取消，改计数，再把最终意图推进 `comment:like:queue`。Cron 每 30 秒最多取 1000 条。先放进 processing 列表，按评论和用户折成最后一次意图，相对数据库做增量。数据库失败就不删 processing，下一轮重放。所以它是至少一次加上最后写入获胜，不是每点一次就插一行。

**他接着问：热门榜怎么算？**

`video:hot:zset`，互动时加分。每 10 分钟乘 0.97，低于 0.01 删掉，超过 200 条丢掉最低的。这是近似热度，不是精确的一小时窗口。热搜是另一个 ZSET，搜索一次加一分，代码里不设过期，重置交给运维。

**他接着问：定时发布存在哪？**

`video:schedule` 这个 ZSET，成员是视频 ID，分数是发布时间的 Unix 秒。到点取出来，把 `videos.status` 从 5 改成已发布。它不是那四条 Cron 之一，是单独的调度器。状态 1 是已发布，2 私密，3 删除，4 待审核，5 定时。删除不是 deleted_at，就是状态 3。

## 7. 搜索

**面试官：视频发布后，搜索多久能搜到？靠什么同步？**

关键词搜索靠 binlog，不是发布接口里双写 ES。River 在同一个进程里用 canal 订 binlog，要求行镜像是 FULL。`videos` 的插入和更新写成 `search_videos` 里 `_id` 为 `videos:{id}` 的文档，删除就删这个文档。标签或 `video_tags` 变了，会反查受影响的视频，整篇重写，不把桥表本身当搜索文档。

位点在 `runtime/river/master.info`，先把 ES 的 bulk 写成功，再记文件名和偏移。写失败就停，位点不往前走，避免「位点过了、文档没有」。批量大约 128 条或 200 毫秒。用户改硬币、改经验只动了 `updated_at` 时，不重建用户搜索文档。

索引用 IK 做中文，再叠拼音子字段，所以拼音首字母也能碰。查询只出已发布。ES 没配或出错时退回 MySQL，那是降级。

**他接着问：关注之后粉丝数在搜索里为什么可能是旧的？**

示例配置订了 `user_focus` 这张表，但没有给它写 ES 规则。没有规则的行事件会被忽略。粉丝数、关注列表、互关列表是在用户文档因为别的原因重建时补上去的。这是配置和代码特殊分支没接上的地方。讲的时候主动说，比被问出来好。

**他接着问：向量搜索和这个索引是一个吗？**

不是。`search_videos_vector` 是 1024 或 2048 维，默认 2048，余弦。发布时用方舟的多模态嵌入写进去，未发布就从这套索引删掉。River 不碰它。查询时 kNN 再和同一索引上的关键词做 RRF，排名常数默认 60。维度改了必须删索引重建。两条链路会短暂不一致。封面参不参加向量由配置决定，相对路径会补成公网地址，本地封面会抓下来变成 data URI。

## 8. 私信

**面试官：私信为什么不放 MySQL？**

两人一份会话，文档 ID 就是较小的用户 ID 加较大的用户 ID，不用自增。未读、会话还显不显示、最后一条预览，都在同一个文档里。发送时先插入消息，再按这个 ID 做一次更新：没有会话就建，接收方未读加一，两边都可见，最后一条换成刚发的。MySQL 要拆会话、成员、消息三张表，还要一个事务把这些对齐。

消息按会话和 `_id` 倒序翻页，索引是 `{conversationId: 1, _id: -1}`。在线推送走 Redis 频道 `chat:user:{用户ID}`，不走 Mongo 的变更流。消息插入与会话摘要更新是两步，当前不能宣称两者构成 Mongo 事务；中途失败可能留下消息与摘要不一致。Mongo 不可用主要影响私信链路，不能把它说成 MySQL 投稿的权威存储。

**他接着问：两台机器，为什么只有一台收得到消息？**

WebSocket 粘在某一台上。发送请求如果打到另一台，必须靠 Redis Pub/Sub 把事件送回持有这条连接的那台。Redis 没有时，代码退成单进程，第二台的连接收不到。这是多实例时要先确认的依赖。

## 9. AI

**面试官：你们的 AI 是怎么接的？Eino 在里面做什么？**

Eino 在这里是模型适配器，没有编排图，也没有把对话存下来。

聊天用 Eino 的 Claude 组件，协议是 Anthropic Messages。示例配置可以指到 DeepSeek 的兼容地址，密钥和地址是单独的三项，没有一个全局 key 兜底。生图用 Eino 的方舟图片模型。生视频和向量用火山的 Ark SDK，因为当时 Eino 没有视频组件。依赖里还有一份 eino 的嵌入和 ES indexer，没有 Go 文件引用它们，向量索引是手写的 dense_vector。

HTTP 上的聊天全是 SSE，包括那个 POST。代码里的非流式函数没有挂路由。正式回答最多 4096 token。没有按次扣硬币。

**他接着问：多轮对话放在哪？**

前端每次把整段 input 传来。服务端默认留最近 20 条、24000 字，系统提示留着，并从前面裁到以用户消息开头。刷新页面之后还记不记得，取决于前端有没有把历史再传回来。模型名里如果带 grok，会被换成配置里的默认聊天模型。代码不调用 xAI。

**他接着问：说「找一部关于猫的视频」时，后面发生什么？**

先用一次最多 256 token 的小调用判断意图，抽出最多 6 个关键词。要找视频时，用方舟把这句话嵌成向量，在向量索引里做 kNN，再和关键词结果融合。向量失败就用 SQL 对已发布视频的标题、简介、分 P 和标签做 LIKE。还没有就取最新的。默认把 8 个候选写进系统提示，要求模型最多回 5 个链接，并且原样抄 `/video/{id}`。聊天里的图片不会当成视觉块发给聊天模型，只变成一句文本标记，只有第一张去参与嵌入。

**他接着问：图片和视频接口有什么不同？**

图片是同步的，张数 1 到 15，参考图最多 14 张，返回的 URL 会改写成站内的资产代理。视频是创建任务，拿 requestID 去轮询，创建时的 URL 不改写。资产代理不登录，但只允许打到火山相关的域名，并且会把 Range 转发给上游。AI 这组路由自己的超时是 90 秒，和配置里给上游客户端的 timeoutSec 不是同一个旋钮。

## 10. 容易被追问的设计取舍

**面试官：你说 DDD，具体体现在哪？有没有过度设计？**

这里的价值主要是隔离变化：`interfaces/http` 只处理协议和参数，`application` 编排投稿、封禁、转码等用例，`domain` 保存业务状态和规则，`infrastructure` 实现 MySQL、Redis、Kafka、存储等端口，`bootstrap` 用 Wire 组装。比如“私密、未来发布、是否审核”如何决定稿件状态在 `internal/domain/video/status_resolve.go`，数据库写入和异步投递由 `internal/application/video/publish_service.go` 协调。读侧为了保留接口形状可直接拼应用 DTO，不能把它宣传成完整的 CQRS 或事件溯源。代价是文件和接口较多，小需求需要跨层定位；收益要用依赖方向和可测试性说明，不能只背目录名。

**他接着问：一次投币成功，到底哪些地方是一致的？**

硬币扣减、投币记录和作者奖励属于 MySQL 事务内的账本，先确保不会重复扣、不会扣成负数；展示计数在事务提交后更新 Redis，失败时有 DB 兜底/缓存失效路径。搜索文档、通知和创作者统计还有异步或后置动作，因此接口响应成功并不意味着所有派生视图同一毫秒更新。排查时先看投币关系和账本，再看 `video:detail:stats:*`，最后看其他视图。代码入口是 `internal/application/video/interact_service.go`。不要用一句“全链路最终一致”把已经在事务里的钱和纯展示计数混为一谈。

**他接着问：视频状态怎么同时处理审核、定时和私密？**

先说优先级：私密直接 Private；公开且指定未来时间，在审核开启时先 Review，否则 Scheduled；立即公开在审核开启时也先 Review，否则 Published。未来时间会进调度 ZSET，但审核开启时到点的 Review 不会自动放行，仍要人工审核。搜索与公开详情也必须按发布状态过滤，不能因为转码产物已经存在就对公众开放。判定见 `internal/domain/video/status_resolve.go`，定时调度见 `internal/application/video/scheduler.go`。

**他接着问：为什么热计数用 Redis，数据库里的数字旧了怎么办？**

高频播放请求若每次都 UPDATE 同一 `videos` 行，会形成热点写入；这里把热计数与稳定的详情元数据拆开，Redis 中的版本和 dirty 集合让 5 分钟回刷时能识别并发变化。它是性能和持久性之间的取舍：MySQL 数值可暂时落后，Redis 在回刷前丢数据则有丢增量风险。若要提高可靠性，应给计数增加可重放的事件日志、或缩小回刷间隔并评估数据库写放大；不能称当前实现“绝不丢数”。见 `internal/application/video/stats_service.go` 与 `internal/infrastructure/scheduler/video_stats_cache.go`。

**他接着问：MySQL 写成功，ES 更新失败时你怎么解释搜索结果？**

关键词索引是 MySQL binlog 派生视图。River 应在 ES bulk 成功后才推进本地位点，失败会停在原位等待恢复，因此出现“详情有，搜索暂时没有”属于同步滞后。向量索引是另一条应用侧同步链路，不能拿 River 位点解释它；改标签还要追查 `video_tags` 触发的受影响视频重建。先看 MySQL 状态是否已发布，再看 River 位点、bulk 错误和 ES 文档，最后区分关键词/向量路径。见 `internal/infrastructure/river/` 与 `internal/infrastructure/search/`。

**他接着问：你们的限流能防住暴力破解吗？**

密码登录前的固定窗口 Redis Lua 计数有两层：同 IP 十分钟 30 次，同一 IP 加账号十分钟 10 次。账号维度带 IP，避免攻击者只知道用户名就把用户在所有网络位置锁死；读取请求体后会复位，后续验证码和绑定仍能读取。Redis 报错时登录限流拒绝请求，这属于安全优先的降级，但会影响可用性。它不能替代验证码、密码强度或针对分布式 IP 的风控。见 `internal/interfaces/http/middlewares/login_rate_limit.go` 和 `pkg/ratelimit/limiter.go`。

## 11. 上传治理与运维追问

**面试官：每天上传 10 个，分片重试会不会把额度扣光？跨午夜怎么算？**

额度按“用户 + 北京时间自然日 + 不同文件哈希”，不是按请求或分片数。Redis Lua 用 Redis `TIME` 算日期，先查同哈希是否已在集合，再检查集合大小，首次加入后把键过期时间设到次日零点；所以同一天同哈希重试不重复占额，跨天是新的自然日。占额发生在首片写入前、秒传确认完整对象时，complete 和投稿还会兜底；失败、取消、未发布都不退。管理员按已分配角色豁免；角色查询或 Redis 不可用时拒绝，避免限额失效。配置默认值见 `internal/application/video/upload_quota.go`、`internal/infrastructure/cache/video/upload_quota.go`。

**他接着问：两个用户传同一个哈希，一个正在合并，另一个正在投稿，清理任务又到了怎么办？**

Redis 的 `video:upload:processing:{hash}` 锁把同一源文件的上传、状态确认、合并、投稿验证及清理协调起来。多分 P 的哈希先去重排序获取，避免互等；锁有两分钟租期并定期续租，用 token 比较后释放，清理用非等待的 TryRun，碰到忙对象就跳过。投稿在锁内复核对象并提交数据库，避免“刚看见对象，清理就删掉”的竞态。它是**租约协调**，不是跨存储事务：Redis 故障、锁续租失败和外部存储长时间不响应仍需靠上下文取消、对象存在性校验及后续对账兜底。见 `internal/infrastructure/cache/video/upload_guard.go`。

**他接着问：未发布的大文件占满 MinIO，怎么安全清？**

Cron 每 5 分钟扫描；未合并分片默认保留 2 小时，未发布源对象默认 1 小时，数值可配置。对每个候选先尝试拿哈希锁；删除源文件前只读查询视频封面、单 P 和分 P 资源是否仍引用路径；真正删除时再次核对存储根、规范化路径和对象最后修改时间。引用查询失败时跳过删除，不能为清空间牺牲已发布视频。对旧 URL 形式还做路径规范化后核对，避免仅凭 `LIKE` 的假命中。清理不能弥补所有对象/数据库双写失败，仍需监控扫描错误和积压量。见 `internal/application/video/upload_cleanup.go`、`internal/infrastructure/storage/upload_garbage.go` 与 `internal/infrastructure/persistence/video/storage_reference.go`。

**他接着问：运营暂停投稿时，为什么不能只隐藏前端按钮？**

客户端可绕过按钮直接调接口。服务端 `VideoSubmissionCheck` 在鉴权后、参数绑定和文件读取前实时读站点开关；普通用户被拒，已分配管理员角色的用户可继续操作，管理员仍过封禁校验。它覆盖视频分片、状态、合并、发布、修改和视频封面接口；通用图片上传因头像、评论等也使用而不受此开关影响。这样热更新生效后不必等前端发版，也不会先耗费上传流量再拒绝。见 `internal/interfaces/http/router/video_router.go` 和 `internal/interfaces/http/middlewares/video_submission_check.go`。

**他接着问：上传状态返回 completed，为什么还要碰对象存储？**

进程内“已完成”缓存只是一条加速线索，源对象可能被硬删、后台清理或存储切换影响。状态接口并行探测完整对象与分片列表；只有对象存储确认存在才返回 `completed=true`，并且在返回秒传前占当天额度。临时网络超时会返回未完成的保守结果，不能把旧缓存当作已经存在的对象。见 `internal/application/video/upload_service.go`。

**他接着问：客户端传的 fileHash 就能证明文件内容没被篡改吗？**

不能。当前服务端主要把 `fileHash` 当作安全的上传标识：先限制可用字符以防路径穿越，合并时校验 `0..N-1` 分片齐全，但没有对最终字节重新计算摘要并与客户端声明比对。相同标识对应已有完整对象时还会复用它；所以不能把现有“秒传”称为密码学意义上的内容校验。若要提供该保证，应在合并后流式计算摘要、比较并只在验证成功后发布对象，另评估跨用户同哈希复用的访问规则。见 `internal/infrastructure/storage/safety.go`、`internal/application/video/upload_service.go`。

**他接着问：你怎么测试上传和清理不会互相删数据？**

先针对可观察的不变量写测试：同一哈希当天重复请求只占一个名额，第 11 个不同哈希被拒；跨北京时间零点重新计数；源对象还被视频/分 P 资源引用时不可删除；引用查询失败或对象在扫描后被更新时也不可删除；清理遇到活跃哈希锁应跳过。仓库现有测试分别落在 `internal/infrastructure/cache/video/upload_quota_test.go`、`internal/application/video/upload_quota_flow_test.go`、`internal/application/video/upload_cleanup_test.go` 和 `internal/infrastructure/cache/video/upload_guard_test.go`。这些替身测试验证决策与竞态分支，真实 MinIO、MySQL、Redis 的联动仍需部署环境集成验证。

## 12. 线上情景（他丢一个现象，你按这个顺序查）

**现象：用户说发布成功了，一直显示转码中。**

先看 `videos` 与初始资源行，再看 Redis `transcode:progress:{视频ID}`。没有进度 key **不能直接推断没有投递**：可能异步任务没跑、投递失败、进度写入失败或 TTL 到期。随后核对 Kafka topic/消费组位点、死信、消费者日志。进度存在时再看 status、stage 和 outTimeSec 是否增长。

不涨：看转码机上 ffmpeg 还在不在。不在，就是进程重启后消息还没被重投，或者永久错误进了死信。在、但是 CPU 接近 0，按现在的实现不应该再出现「上传把滤镜堵死」，要看是不是看门狗还没到点。看门狗是片长的三分之一，最短也要 20 分钟。

涨了但是详情没有新清晰度：看 `video_resources` 或分 P 资源有没有对应行、对象是否真的可读，再看详情缓存代数和失效日志。资源已落而缓存失效失败时，通常需等元数据缓存 TTL 后重建；不能只凭 Redis 进度判断成片可播。

**现象：播放量和后台对不上。**

详情优先读 Redis 热计数，后台如果读 `videos.views`，正常情况下会有一个回刷周期的延迟；Cron 失败、跳过或 Redis 异常时不能保证“最多 5 分钟”。再看 dirty 集合里这个 ID 还在不在，版本号是不是持续变化。刷库时版本变了会保留脏标记给下一轮。Redis 被清空过，则未回刷增量可能找不回来。

**现象：刚发布的视频，标题搜索没有，分区页有。**

分区页读 MySQL。搜索读 ES。先看 River 进程还在不在跑，`master.info` 的位点还在不在涨。位点不涨，就是 bulk 写失败后故意停住，避免跳过没写进去的行。位点在涨但文档没有，看视频 status 是不是还在审核或定时，查询只出已发布。标签改了却没更新搜索，走的是 `video_tags` 反查重写，不是改 `videos` 那一行。

**现象：封禁了，用户还能调接口。**

先确认调的是哪类接口：`JwtAuth` 拦永久封禁，临时封禁由相应内容写接口的 `UserBanCheck` 拦，其他已登录接口可能仍可读。再查 MySQL 的 `users.status` 和最新封禁记录是否一致，随后查 `user:status:{id}`、generation 和封禁后写穿 Redis 是否报错。旧缓存读在写穿失败时可能持续到 TTL 到期；正常写穿后不应简单归因于“等 60 秒”。到期临时封禁还可由 Cron 或内容请求触发解封。

**现象：评论点赞数跳，或者点了没加上。**

接口先改的是 Redis set 和计数，24 小时过期。库里的 `comment_likes` 要等 30 秒的队列。processing 列表不空，说明上一批刷库失败，正在重放，这时页面上的数和库不一致是预期。队列里的 JSON 全坏会被丢掉，那一批意图就没了。

**现象：只有连在某一台机器上的用户收得到弹幕或私信。**

连接在本机内存里。跨机器靠 `danmu:channel:{视频}:{分P}` 或 `chat:user:{id}`。Redis 订阅失败会退成单进程。再看弹幕最近列表是不是只有本机写进去的：那是 `danmu:recent` 这条 list，和 Pub/Sub 是两回事，列表丢了只影响后进来的人补历史，不影响正在推的那一条。

**现象：AI 找视频总是返回最新的几部，和问题无关。**

意图分析没抽出关键词，或者向量调用失败，会退到 LIKE，LIKE 也空就取最新已发布。先看方舟密钥和向量索引在不在，维度是不是 1024 或 2048 且和索引一致。维度不一致不会自动改映射，必须重建。视频如果还没发布，向量索引里会被删掉，搜不到是对的。

## 13. 他问「如果再做，你先改什么」

按“影响、现有证据、最小改法、如何验证”回答。优先补**投稿入库与 Kafka 投递之间的可靠性缺口**：把待投递事件和稿件放在同一 MySQL 事务，后台投递成功再标记，或先做可重扫的待投递表与对账任务。这样能处理“稿件已经存在，但转码进度一直没有”的真实故障；用注入 Kafka 故障和进程重启的集成测试验证不漏投、重投可幂等。

第二步视转码负载把消费者与 API 分开部署，分别设资源配额和健康检查；这主要解决资源争用，不会自动修复投递缺口。再考虑给关键词用户索引补齐 `user_focus` 变化触发，以及为热计数增加可重放来源。登录若要做服务端吊销，需要新增 refresh token 状态或版本号与校验流程；当前不能说 refresh 已可吊销，也不能认为 JWT 一改就解决临时封禁的权限范围问题。

面试中只选与你负责模块最相关的一项展开，讲清上线前要补哪类故障测试和观测指标。
